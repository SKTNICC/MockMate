# MockMate 文档规范

> 更新日期：2026-11-19 ｜ 状态：生效中 ｜ 适用范围：`docs/` 目录下全部公开工程文档

本规范面向所有参与 MockMate 的协作者（产品、Android、后端、联调）以及辅助开发与复审的 AI 模型。新增、修改、移动或归档项目文档时，请直接按本规范执行。

---

## 1. 适用范围与边界

- **纳入范围**：`docs/` 下纳入 Git 管理的公开工程文档（产品定义、工程进度、本地开发说明、阶段交接与验收记录、审查整改与排查复查文档）。
- **不纳入范围**：`.gitignore` 中声明的本地私有或临时目录（如 `/开发文档/`、`/题库材料筹备/`、`/产品设计/`、`/队友文档/`、`outputs/`、`.work/` 等）不进入 `docs/`，也不应在 `docs/` 中指向这些未提交目录。
- **模块入口 README**：仓库根目录 [README.md](../README.md)、[android/README.md](../android/README.md)、[backend/README.md](../backend/README.md)、[fixtures/m1/README.md](../fixtures/m1/README.md) 保持在各自模块目录，负责模块级快速启动与入口跳转；系统级文档统一归档在 `docs/`。

## 2. 目录结构规范

### 2.1 标准目录树

```text
docs/
├── README.md                              # 文档总索引（导航入口）
├── 文档规范.md                             # 本规范（根目录唯一规则文档）
├── overview/                              # 项目级常驻文档（原地持续更新）
│   ├── 产品定义与阶段里程碑.md
│   ├── 工程进度.md
│   └── 本地开发.md
└── M2/                                    # 阶段目录（按里程碑 M1/M2/M3... 划分）
    ├── README.md                          # 本阶段文档索引与整改归档状态
    ├── M2文字模拟面试开发交接.md           # 本阶段核心开发交接/设计文档
    ├── M2验收记录.md                      # 本阶段验收与测试环境记录
    └── fixes/                             # 本阶段审查整改、排查与复查记录
        ├── m2-review/                     # 专题 1：M2 主流程审查与复审
        ├── skill-catalog/                 # 专题 2：技能标签与 AI 解析修复
        ├── match-and-plan/                # 专题 3：匹配证据、出题去重与槽位缓存
        └── ai-output-and-parse/           # 专题 4：AI 返回边界、材料解析与任务恢复
```

### 2.2 目录命名规则

- **顶层功能目录与专题目录**：统一使用**小写英文**（kebab-case，如 `overview`、`fixes`、`ai-output-and-parse`），避免中文目录名在 Git 日志、Shell 脚本或跨平台终端中被转义。
- **里程碑目录**：统一使用**大写 `M` + 数字**（如 `M2`、`M3`、`M4`），禁止把 M2 的过程文档放进 `M1` 等错位目录。
- **专题目录 `<topic>`**：按业务模块或故障专题聚合（建议 2–6 个词以内、小写连字符），同一专题的多轮审查/复查放在同一 `<topic>/` 下；若为跨模块单次小修复且不宜单开专题，可归入 `fixes/misc/`，保持 `docs/M<n>/fixes/<topic>/` 目录深度一致。

### 2.3 「新文档该放哪？」速查表

| 文档类型 | 存放路径 | 维护方式 | 示例 |
|---|---|---|---|
| 文档总索引 / 规范本身 | `docs/` 根目录 | 原地更新 | `docs/README.md`、`docs/文档规范.md` |
| 全项目产品定义、里程碑、工程进度、环境搭建 | `docs/overview/` | 原地覆盖更新 | `docs/overview/本地开发.md` |
| 某里程碑的开发交接、接口与状态机设计 | `docs/M<n>/` | 原地更新（附更新日期与代码基线） | `docs/M2/M2文字模拟面试开发交接.md` |
| 某里程碑的测试与验收结论 | `docs/M<n>/` | 原地更新或按轮追加记录 | `docs/M2/M2验收记录.md` |
| 审查整改、故障排查、多轮复查指南 | `docs/M<n>/fixes/<topic>/` | **每轮新增文档**，不覆盖历史记录 | `docs/M2/fixes/ai-output-and-parse/2026-11-19-03-...md` |

### 2.4 新建里程碑目录（如 `M3/`）步骤

当进入新阶段（例如 `M3`）时，按以下顺序初始化：
1. 新建 `docs/M3/` 与 `docs/M3/README.md`。
2. 在 `docs/M3/` 下创建 `M3<主题>开发交接.md` 与 `M3验收记录.md`（使用第 4 节模板）。
3. 后续所有针对 M3 的代码审查、真机排查与整改复查均放入 `docs/M3/fixes/<topic>/`。
4. 更新 [docs/README.md](README.md) 和仓库根目录 [README.md](../README.md) 中的阶段入口链接。

## 3. 文件命名规范

### 3.1 各类文件命名格式

1. **根目录固定文件**：`README.md`、`文档规范.md`。
2. **项目常驻文档（`docs/overview/`）**：语义化中文名，**不带日期前缀**（如 `工程进度.md`、`本地开发.md`），避免产生多份日期副本。
3. **阶段核心交付文档（`docs/M<n>/`）**：以里程碑编号开头，无日期前缀，例如 `M2文字模拟面试开发交接.md`、`M2验收记录.md`（未来如 `M3语音模拟面试开发交接.md`、`M3验收记录.md`）。
4. **审查整改 / 排查复查文档（`docs/M<n>/fixes/<topic>/`）**：
   - 固定格式：`YYYY-MM-DD-NN-<中文简明标题>.md`
   - `YYYY-MM-DD`：文档创建日期（例如 `2026-11-19`）。
   - `NN`：同一 `<topic>/` 目录下从 `01` 开始递增的两位轮次编号（`01`、`02`、`03`…），保证按文件名排序即时间与复查顺序。
   - `<中文简明标题>`：简明概括本轮主题，控制在 20 个汉字以内，不包含标点或空格。

### 3.2 命名禁止项

- 禁止在 `docs/` 根目录直接堆放过程文档、排查文档或临时说明。
- 禁止把属于 `M2`（或当前阶段）的文档放进 `M1` 等其他阶段目录。
- 禁止在文件名中使用空格、括号、以及 `v1`、`v2`、`final`、`最终版`、`修改版`、`最新` 等模糊后缀。

## 4. 文档元信息与模板

所有正式文档在 `# 一级标题` 之后、正文之前，应提供一行或一段**元信息**，明确：**更新日期**、**当前状态**、**适用阶段**、**代码基线（commit 哈希或工作区状态）**、**前置/关联文档**。

以下 3 套模板可直接复制使用。

### 模板 A：阶段开发交接 / 设计文档（`docs/M<n>/M<n><主题>开发交接.md`）

````markdown
# MockMate M<n> <主题>开发交接

> 更新日期：YYYY-MM-DD ｜ 状态：设计中 / 开发中 / 待验收 ｜ 代码基线：`<commit>` ｜ 适用对象：后端、Android、联调负责人

前置阅读：[工程进度](../overview/工程进度.md) · [本地开发](../overview/本地开发.md) · [产品定义与阶段里程碑](../overview/产品定义与阶段里程碑.md)

## 1. 阶段目标与执行边界

- 本阶段必须交付的用户旅程与验收标准。
- 沿用的产品方向与工程默认参数。
- 明确不在本阶段范围内的能力。

## 2. 数据模型、迁移与契约变更

- 新增/修改的数据库表与 Alembic 迁移版本说明。
- 共享契约修改先改 `tools/m1/build_contracts.py` 并同步生成物。

## 3. 接口与状态机口径

- 新增/修改 API 路径、鉴权与幂等键要求、错误码与恢复边界。
- 服务端与客户端各自维护的状态边界。

## 4. 后台任务与 AI 调用约束（如涉及）

- 任务类型、重试策略、模型输出校验与兜底策略。

## 5. 联调与验收口径

- 必测正常闭环与异常恢复用例列表。
````

## 5. 内容编写、事实准确性与安全脱敏规范

### 5.1 结论先行与结构清晰

- 整改/交接类文档必须在开头给出**执行顺序、优先级（P1/P2/P3）和完成标志表**，避免接手人或模型通篇翻找结论。
- 区分「**已复现**（给出复现方式）」「**只读核查确认**」「**代码走读发现**」，不要把推测当成已复现事实。

### 5.2 事实口径与验收边界

文档中必须严格区分以下四种状态，禁止混淆表述：
1. **已实现**：代码和接口已编写并合入分支，不等于已测试通过。
2. **单测 / 合成闭环通过**：在 `AI_PROVIDER=test`、`test_only` fixture 或模拟 HTTP 下验证通过。**禁止将合成测试结论写成“真实 AI 已验收”或“已可正式上线”。**
3. **真机 / 真实模型已验收**：在真实手机和真实服务端配置下完成约定旅程，且保留脱敏证据。
4. **未实现 / 受阻**：明确写出阻塞原因与前置条件（如真实双人审核未签发、真机 instrumentation 环境异常等）。

### 5.3 安全与脱敏红线

- **严禁写入仓库**：真实 `.env` 内容、API Key、Bearer Token、登录密码、数据库口令、签名密钥（`.jks`/`.keystore`）、真实个人简历/JD、本机绝对路径（例如 `C:\Users\...` 或 `D:\code\...`）。
- **命令与配置示例**：所有密码、密钥、个人路径一律使用占位符，例如 `<本机密码>`、`<API_KEY>`。
- **日志与验收记录**：只保留脱敏后的 UUID、状态值、脱敏账号前缀和稳定错误码；不粘贴完整个人材料原文或模型思考文本。
- **禁止外部私人路径**：文档内不要链接到本地 `.gitignore` 忽略目录或仓库外的私人文件。

### 5.4 编码与格式

- 所有 Markdown 文件必须使用 **UTF-8（无 BOM）** 编码、**LF（`\n`）** 换行符（与根目录 [.gitattributes](../.gitattributes) 保持一致）。
- Windows PowerShell 下注意避免 `Set-Content` 或 `>` 重定向写入默认编码/CRLF；建议用编辑器或显式 `encoding="utf-8", newline="\n"` 生成。

## 6. 链接与代码引用规范

- 仓库内互相引用一律使用**相对路径**与**正斜杠 `/`**，严禁写本机绝对路径或 `file://` 链接。
- 各层文档常用相对路径前缀速查：

| 当前文档所在位置 | 链接到仓库代码（如 `backend/...`） | 链接到 `docs/overview/...` | 链接到 `docs/M<n>/...` | 链接到同专题其他文档 |
|---|---|---|---|---|
| `docs/` 根目录 | `../backend/...` | `overview/...` | `M2/...` | `M2/fixes/<topic>/...` |
| `docs/overview/` | `../../backend/...` | 同级文件名（如 `本地开发.md`） | `../M2/...` | `../M2/fixes/<topic>/...` |
| `docs/M<n>/` | `../../backend/...` | `../overview/...` | 同级文件名（如 `M2验收记录.md`） | `fixes/<topic>/...` |
| `docs/M<n>/fixes/<topic>/` | `../../../../backend/...` | `../../../overview/...` | `../../M2验收记录.md` | 同级文件名（如 `2026-11-18-01-...md`） |

- 引用代码位置时尽量写到具体文件路径（可选附带 `#L行号`），如：
  `[runner.py](../../../../backend/app/workers/runner.py)`。
- **移动或重命名文档时的联动规则**：必须同步检查并更新所有引用处，至少包括：
  1. 仓库根目录 [README.md](../README.md)
  2. [android/README.md](../android/README.md) 与 [backend/README.md](../backend/README.md)
  3. [docs/README.md](README.md) 与对应阶段 [docs/M2/README.md](M2/README.md)
  4. 其他文档内部的交叉链接

## 7. 生命周期与日常维护流程

1. **新增文档**：先查第 2.3 节决定放置目录 → 按第 3 节命名 → 套用第 4 节模板填写元信息与正文 → 在对应阶段 `README.md`（或 `docs/README.md`）登记。
2. **常规更新**：`docs/overview/` 与阶段核心文档（交接、验收记录）原地更新并刷新顶部更新日期与代码基线，不保留多份日期副本。
3. **多轮整改与复查**：每轮审查或专项复查在 `docs/M<n>/fixes/<topic>/` 下新建递增序号文件（`01`、`02`、`03`…），在文首链接上一轮文档，不改写历史轮次的原始结论。
4. **整改合入归档**：当某一批整改文档对应的代码已经提交并合入主干后，及时在 `docs/M<n>/README.md` 索引表中将该文档状态更新为 `已合入 <commit>`，并在 `docs/overview/工程进度.md` 同步最新模块状态与测试基线，防止后续协作者把已关闭的历史整改单误当成未完成任务。

## 8. 提交前自查清单

提交任何新增或调整的文档前，请逐项确认：

- [ ] **位置正确**：没有把阶段/过程文档放到 `docs/` 根目录，也没有跨阶段放错（如把 M2 放进 M1）。
- [ ] **命名合规**：`fixes/<topic>/` 使用小写英文 kebab-case；整改文件符合 `YYYY-MM-DD-NN-<标题>.md`。
- [ ] **元信息完整**：写明了更新日期、状态、代码基线与适用阶段。
- [ ] **索引同步**：已在 `docs/README.md` 或 `docs/M<n>/README.md` 中添加或更新条目及状态。
- [ ] **链接有效**：所有相对路径使用 `/`，移动或改名后无死链。
- [ ] **口径严谨**：已明确区分 `test` provider / 合成数据与真实 AI / 真机验收，未夸大验收结论。
- [ ] **安全脱敏**：无真实密钥、密码、Token、个人隐私材料和本机绝对路径。
- [ ] **编码干净**：UTF-8（无 BOM）+ LF 换行。
