# AI 模拟面试 App：产品定义与阶段里程碑

更新日期：2026-11-15。当前状态：第一版完整产品方案，供整体评审。

本文持续维护已经确认的产品方向，以及据此整理的功能、流程与阶段方案。表中明确注明“用户已确认”的是需求决定；其他页面组织、默认参数和里程碑是本次提出的设计建议，尚不等于用户逐项认可。当前不编写项目代码；里程碑描述未来的交付目标，不表示已经开始或完成开发。

## 1. 已确认的产品方向

| 项目 | 用户已确认的要求 |
|---|---|
| 目标用户 | 准备实习、校招的大学生 |
| 岗位范围 | 主要覆盖计算机相关岗位；具体岗位名单和首个岗位尚未确定 |
| 产品目标 | 展现从准备、面试到结果反馈的全流程，并考虑课程结束后继续完善 |
| 时间安排 | 不以课程截止时间压缩功能；按阶段交付，进度由小组掌握 |
| 开发边界 | 先完成产品设计，再进入项目代码开发 |
| 开发协作 | 前后端分离；用户负责产品与 App，一位同学负责后端和服务器 |
| 课程约束 | 没有指定技术要求；既有技术选型仍为建议 |
| 反馈方式 | 正式模拟整场结束后出报告；专项练习逐题点评，两者分开 |
| 开始条件 | 简历和 JD 都必须具备；JD 可由用户提供，也可选择内置岗位 JD |
| 录像单位与内容 | 每道题一份本地视频；保存数字人主屏和自拍小窗组成的完整面试界面，包含问题与本人作答 |
| 正式面试题目来源 | 题库与 AI 生成各占一半；以主问题为统计口径的细则见第 2.4 节 |
| 专项练习个性化 | 支持用户描述本次训练需求，以类似备注的方式参与 AI 出题 |

产品当前可表述为：

**面向计算机相关岗位实习与校招的 AI 模拟面试 App，结合简历和目标岗位组织多轮问答，通过文字、语音或带数字人形象的视频界面完成模拟面试，并用报告、回放和持续训练帮助用户改进。**

“带数字人形象的视频界面”采用预置视频素材呈现；用户画面不进入 AI 视频分析。

## 2. 最终功能与应用结构

以下九项来自用户最初提出的核心需求，仍是最终产品范围的基础：

1. 简历上传和解析：教育、工作、项目、技能与技术栈。
2. 目标 JD 输入、上传，或选择内置岗位 JD。
3. 简历与 JD 分析：岗位要求、经历支持、优势和待验证项。
4. 根据简历、JD、岗位、级别与题库制定个性化计划。
5. 文字、语音、视频三种模拟面试模式。
6. 根据回答进行追问，保留多轮上下文。
7. 分析回答、评分并提取依据。
8. 生成包含表现、问题和改进建议的结构化报告。
9. 保存历史、支持专项练习与同题复练，建立训练画像并观察长期变化。

建议三种模式共用材料、计划、问答、追问和报告体系。用户选择的是交互方式；视频模式增加本地录像和数字人呈现，不另建一套评分逻辑。

### 2.1 两种训练场景，三种交互方式

两种场景回答“这次怎样训练”，三种交互方式回答“用户怎样作答”。它们是两个不同选择。

| 场景 | 目标与过程 | 反馈方式 |
|---|---|---|
| 正式模拟 | 按计划经历开场、主要问题、追问和收尾，保留整场连续感 | 过程中不展示分数、答案和教学点评；结束后统一报告 |
| 专项练习 | 针对选定能力、题目或报告薄弱项练习，允许反馈后再答 | 每题结束后给点评、依据和改进思路；新尝试单独保存 |

| 交互方式 | 主要体验 | 记录 |
|---|---|---|
| 文字 | 阅读问题、输入回答、文字追问 | 问答、评价与报告 |
| 语音 | 播放问题、录音回答、转写分析、语音追问 | 问答、转写、评价；音频保留规则后续明确 |
| 视频 | 数字人主屏、自拍小窗，语音轮流交互 | 与语音相同的分析记录，加每题完整界面的本地录像 |

建议最终两种场景均能复用三种交互方式，按依赖逐步开放。视频只改变呈现和回放能力，不能因为打开摄像头就多出表情、姿态或自信评分。

### 2.2 功能模块

| 模块 | 最终应包含的功能 | 主要规则 |
|---|---|---|
| 简历资料 | 上传、解析教育／工作／项目／技能、核对修改、选择当前版本 | 没有工作经历允许为空；不编造经历；保留本场使用的版本 |
| JD 资料 | 自备 JD 粘贴／上传、内置岗位 JD 选择、要求核对 | 所有正式面试具备一份明确 JD；内置模板不是虚构招聘信息 |
| 材料分析 | 岗位要求与经历对应、优势、薄弱项与待验证项 | 简历未体现不直接等于不会；指出依据 |
| 面试计划 | 选择岗位／级别、考察方向、主问题数量与模式，确认开始；题库和 AI 混合组题 | 计划绑定材料、来源和评分规则；正式模拟题库／AI 各半，细则见第 2.4 节 |
| 正式模拟 | 开场、逐题回答、有限追问、重复问题、跳过、暂停／提前结束、收尾 | 正式过程中不给答案；不因系统失败扣能力分 |
| 专项练习 | 按能力或报告入口练题、填写训练备注定制生成、逐题点评、同题重答 | AI 定制练习不强制套用正式面试的各半比例；保留需求与旧回答 |
| 面试报告 | 概览、能力表现、逐题分析、原话依据、建议和下一步训练 | 显示覆盖度；缺证据时不强行给确定结论 |
| 历史与回放 | 按场次查看材料、问答、报告；视频模式逐题播放本地录像 | 文件缺失如实提示；没有云端视频备份 |
| 能力画像 | 按岗位与能力查看多次训练记录和薄弱项变化 | 只比较相近口径；区分练习与正式模拟；显示样本范围 |
| 账户与本地管理 | 登录／退出、本人数据访问、材料与记录管理、本地视频空间与删除 | 跨账号隔离；视频删除与报告删除的影响要明确 |

内置 JD 建议展示岗位、实习／校招级别、职责、技能要求和模板版本，标注为“内置练习岗位”。用户应能在开始前阅读并确认，不能只显示一个岗位名却隐藏实际考察要求。最终应支持复用已上传的简历和已选 JD，无需每次重复上传，但每次面试都要绑定明确材料。

### 2.3 页面组织建议

建议底部先采用四个栏目，后续界面设计时再验证布局：

| 栏目 | 主要内容 |
|---|---|
| 首页 | 开始正式模拟、最近一次训练摘要、继续未完成面试 |
| 专项练习 | 按岗位与能力选择练习、填写备注进行 AI 定制、从报告进入薄弱项复练 |
| 记录 | 正式与专项记录分组，进入问答、报告和逐题视频回放 |
| 我的 | 简历、JD 资料、账户、默认偏好、本地录像管理 |

关键页面依次为：资料选择 → 简历／JD 核对 → 对应分析 → 计划确认 → 模式与设备检查 → 面试间 → 结束与报告 → 单题详情／回放／重练。这里确定页面职责，尚未确定视觉风格或制作可交互原型。

岗位内容逐步覆盖计算机相关方向，例如后端、前端、移动端与 AI 相关岗位；首个岗位和完整名单留到内容规划时确定。不能仅把同一套题换岗位名称就声称已经覆盖新岗位。

### 2.4 正式模拟：题库与 AI 各半

用户已提出正式面试采用题库与 AI 生成各一半。建议落实为**每场计划中的主问题各占 50%**，而非每次抽题有 50% 概率来自题库。以下统计和异常细则为本次设计建议：

| 项目 | 规则建议 |
|---|---|
| 统计单位 | 只统计主问题；追问、寒暄和收尾不另占来源配额。自我介绍若作为独立考察主问题，则正常计入 |
| 题量选择 | 正式模拟优先提供偶数主问题数量；默认 6 道仍是待评审建议，对应 3 道题库＋3 道 AI |
| 题库部分 | 从适合岗位、级别与能力目标的审核题中选取，保留题目版本及评价依据 |
| AI 部分 | 结合简历、JD、待验证项生成本场新主问题，同时生成考察目标、参考思路与评分要点 |
| 排序 | 按面试节奏组织，不必机械地一道题库、一道 AI 交替 |
| 追问 | 两种来源的主问题都可以追问；根据实际回答生成，并受同一次数和停止规则约束 |
| 题目不足或生成失败 | 先重试生成、调整可选题目或提示用户重新准备；不能静默改变来源比例或拿未审核题补题库份额 |
| 中途结束 | 各半是开始时计划比例；用户提前退出后，实际作答来源可能不再各半，报告如实统计 |

需要分开保存两种信息：

- **来源：**题库选题或本场 AI 新生成。
- **出题依据：**简历项目、JD 要求、能力缺口或岗位基础。

因此，一道从题库选出的项目题仍属于题库来源；AI 重新组织了措辞、念题或生成了追问，都不会使它自动变成一条 AI 新题。对已有题只换姓名、项目名或措辞，也不应拿来凑 AI 配额。AI 生成时参考题库可以，但若最终决定复用原题，就应按题库计数，另补 AI 槽位。

题库的一半提供相对稳定、可复核的考察内容，AI 的一半服务于材料中的具体经历和待验证项。两部分都要与岗位和用户材料相关，不能把题库部分做成不看简历的随机抽题。

### 2.5 专项练习：用一个备注框表达个性化需求

专项练习增加“AI 定制练习”入口，复用已选择的简历、JD、岗位与级别，额外提供一个可选输入框：**这次想重点练什么？**

示例：

> 重点练 Java 集合和并发，结合我简历中的课程项目，保持实习难度，先不要算法题。我经常只会背结论，希望多问原因和实际应用。

界面不要求用户自己编写 Prompt，也不必重新填写已有资料。用户输入的是训练需求，系统将它与既有材料共同提供给生成流程；备注为空时，按选定岗位或薄弱项生成。

建议流程为：**选择／确认材料 → 填写本次训练备注 → 查看系统理解的训练重点 → 生成题目 → 作答与追问 → 逐题点评 → 再练或下一题。**训练重点可以是一句简短摘要，让用户有机会在开始前纠正误解，不增加一套冗长表单。

规则建议：

1. AI 定制练习可以全部使用生成题，不强制正式模拟的 50% 比例；已有题库练习和报告原题复练继续保留。
2. 备注可以影响主题、侧重点、题型偏好、题量诉求、希望加强的能力和排除项；实际采用的难度和数量在生成前展示。
3. 备注不能替代必需的简历或 JD，也不能要求编造经历、修改已提交回答或预设高分。
4. 备注与已选岗位、级别或出题规则矛盾时，说明冲突，请用户修改本次设置；不能一边显示实习难度，一边暗中出资深题。
5. 生成后检查题目是否落实了允许的训练需求、是否重复、是否仍与目标相关；不能只把备注拼进 Prompt 就假定已经满足。
6. 本次备注、系统理解的重点和实际题目随练习记录保存；以后修改默认备注不改变旧记录的含义。

备注直接影响新主问题；后续追问也可继承相同重点，但必须首先针对用户刚才的回答，不为了满足“多追问”而重复或强行追问。

### 2.6 生成题的评价与沉淀

在线生成题是本场或本次练习的题目，不因生成成功就自动成为公共审核题库的一员。生成时同时准备能力目标、参考思路、关键点、合理替代解和量表；检查生成内容与材料是否一致。模型的自检声明不等于事实已经核实。

AI 生成的参考答案属于辅助依据，不能作为唯一权威标准，特别是技术细节与用户项目事实。生成题可以提供训练参考评价；发现技术依据冲突或不足时，说明不确定项，必要时不计入确定性的专业分，而不是强行按模型自己的答案判错。报告记录题目来源和实际采用的评价依据。

经后续审核的优质生成题可以进入公共题库；以后从公共库复用时，按本场的“题库来源”计算，而不是因最早由 AI 创作就永久算生成题。当前不新增题库管理后台或自动审批功能。

### 2.7 现有 Prompt 资产的适配边界

本次实际检查了 [计划模板](../题库材料筹备/prompt-library/03_question_planner.v1.md)、[单题生成模板](../题库材料筹备/prompt-library/04_question_generator.v1.md)、[追问模板](../题库材料筹备/prompt-library/05_followup_agent.v1.md) 和 [评分模板](../题库材料筹备/prompt-library/06_answer_scorer.v1.md)。它们提供基础设计，还不是已接入、已验证的应用能力。

| 当前内容 | 与本轮产品规则的差别 | 后续适配方向 |
|---|---|---|
| 计划模板要求题库原题不超过 50%，允许解释后微调 | 不等于正式面试固定各半 | 分配并核验主问题来源配额；用户提前结束时另记实际覆盖 |
| `source` 混用 bank、resume、jd、generated | 把题目来源和出题依据混在一起 | 来源与材料锚点分开，避免统计含混 |
| 生成模板支持 `reuse`，相似时可直接转复用 | 复用会影响最终各半比例 | 复用按题库计算，不能仍占 AI 新题槽位 |
| 生成模板要求能展开两分钟以上 | 与每次回答最多 120 秒的交互不一致 | 主问题允许在 120 秒内表达核心，深入部分通过有限追问展开 |
| 现有输入未明确接收专项训练备注 | 用户定制诉求无法稳定传递 | 增加独立训练需求输入，并贯穿生成、追问和结果检查 |
| 生成答案标记 `model_generated`，提示尚未核验 | 不能直接当作权威标准或公共审核题 | 保留生成状态与依据，区分当前训练使用和公共题库收录 |

来源比例、必需材料、题目归属和追问上限需要由后续业务流程共同约束，不能只写一句 Prompt 就视为已经实现。本轮只调整产品设计，未改写这些 Prompt 文件，也未编写项目代码。

## 3. 视频模式的确定形态

### 3.1 画面和声音

- 主体区域：数字人面试官。
- 左上角小窗：用户前置摄像头的自拍视角，形成类似视频通话的布局。
- 数字人素材：预先准备“聆听”和“说话”两种状态的视频。
- 面试官声音：根据本轮要表达的内容生成语音，在手机上播放。
- 用户录像：每道主问题一份完整面试界面的视频，自动保存到手机本地，提供按题回放入口。
- AI 处理：使用音频转写后的内容分析回答，不上传用户视频，不分析表情、视线或姿态。

预置“说话”视频与生成语音的精确口型同步不是当前已经提出或验证的能力，不以此作为宣传承诺。

### 3.2 一次作答的交互循环

**面试官播题 → 用户录音作答 → 音频转写 → 分析并决定下一步 → 生成需要说给用户听的话 → 合成并播放语音。**

其中“分析”与“对用户说的话”分开：正式模拟中模型可以判断缺口，但面试官播放的是追问、下一题、转场或收尾，不把评分和参考答案读出来。专项练习则在本题结束后展示点评，是否额外朗读长点评可后续配置，不要求每次都全文播报。

### 3.3 两种视频素材，配合明确的操作状态

下表为建议交互规则：

| 操作状态 | 数字人呈现 | 用户应看到什么 |
|---|---|---|
| 面试官播题或追问 | 说话视频 | 当前问题／字幕、正在播放 |
| 等待用户开始回答 | 聆听视频 | 开始回答入口；倒计时尚未启动 |
| 用户作答 | 聆听视频 | 正在录音、120 秒倒计时、提前结束入口 |
| 上传、转写和分析 | 聆听视频配状态提示 | 回答已结束、正在处理；不再显示录音中 |
| 处理失败 | 保持稳定画面，明确提示 | 已保存情况，以及重试或恢复入口 |
| 面试结束 | 聆听画面或结束页 | 报告状态、本地回放入口 |

不需要为了“正在分析”再增加第三种数字人视频；用状态文字即可区分。动画播放状态不能被当作音频真正开始或结束的依据。

### 3.4 120 秒的含义

用户明确要求每次回答显示 120 秒倒计时。建议默认规则：从本次实际开始录音起计时，面试官播题、网络等待、转写和分析不占用该时间；用户可以提前结束，到时停止录音、保存并提交本次有效作答。失败时保留待提交内容，不以新回答重复推进。这个自动提交规则属于本次设计建议。

这应按“每次录音回答”理解，不能据此默认整道题连同追问只有 120 秒。一道题含主问题和追问时，对应的视频可以超过 120 秒；送去识别的仍是每次单独作答的音频，不能把整题长视频音轨一次性提交。

截至本次核对，DeepSeek 官方 ASR 为整段音频请求，不支持流式识别，单次最长 120 秒，另有 8 MiB 和音频格式限制。因此产品上的 120 秒还需要后续验证实际录音文件的时长、大小和兼容格式，不能只依赖画面倒计时。[官方 ASR 指南](https://api-docs.deepseek.com/zh-cn/guides/asr/)

### 3.5 本地录像与音频分析的边界

视频只在手机本地保存和播放；需要在手机端得到可提交的音频，或在本地提取、转换音轨，不通过服务器接收用户录像来完成。

Android 的录像能力可包含画面、音频和文件保存，但具体如何同时满足本地录像与独立音频提交，还需要在进入开发后验证，当前不锁定实现方式。[Android CameraX 文档](https://developer.android.com/media/camera/camerax/video-capture)

### 3.6 每题完整界面录像的规则

用户已选择“每道题一份视频，包含问题与本人作答”，并明确保存完整面试界面。建议将“每道题”定义为一条主问题及其关联追问，连续保存在同一题的录像中；这个追问归组方式是本次建议。

正常一题的视频包含：主问题播放、本人回答、关联追问与补充回答，并保留真实发生顺序。回放能看到数字人与本人小窗，也能听到面试官与本人的声音。用户戴耳机时，不能因麦克风收不到扬声器声音而丢失问题声音。

需要分别验收三个结果：

1. 面试间实时画面正确。
2. 本地保存的视频确实包含完整界面和双方声音，而非只有前置摄像头画面。
3. 送去 AI 的音频只对应当前用户作答，不混入面试官播报。

完整界面录制／合成、声音同步和本地音轨准备需要在视频阶段专门验证；不因相机预览可用就视为视频模式完成。录像范围建议限定为应用内面试画面，切出应用后暂停／结束本段录制，不录入其他应用内容。

每题视频在该题结束后完成保存，面试结束后从题目详情进入回放。中断时尽可能保留可播放片段，并标记本题录制未完整完成；不能把损坏文件显示为成功保存。断网不应删除已保存录像，存储不足或权限问题则明确告知并让用户选择后续操作。

本地录像可按面试与题目管理、播放和删除。更换设备、文件被用户删除或应用数据被清理后，历史报告不能承诺恢复视频；应提示“本地视频不可用”。视频不云同步，报告与问答的保存位置与生命周期另外明确。

## 4. 完整使用流程与默认规则

### 4.1 正式模拟

**选择目标岗位与级别 → 选择简历 → 上传／输入 JD 或选择内置 JD → 核对材料 → 查看分析与计划 → 选择面试模式 → 设备与录制确认 → 开场 → 逐题问答与追问 → 收尾 → 报告 → 回放与后续训练。**

计划阶段按题库／AI 各半准备主问题与评价依据，并核验来源和重复情况；面试开始后不因追问数量改变主问题配额。正式模拟仍保持面后统一点评。

简历和 JD 缺一不可。缺材料时保留准备进度，引导补齐，不能自动把个性化面试变成无材料通用问答。

建议面试内容从自我介绍／开场进入项目经历、岗位基础与场景、行为沟通，最后反问和收尾；具体配比由岗位与材料决定，不要求每场机械采用相同顺序。用户反问时，AI 说明自己是在模拟岗位面试，不冒充真实企业招聘人员。

正式模拟的重点是连续体验：允许重复问题、跳过、暂停和提前结束；完整点评统一在面后展示。跳过与系统失败分别记录。提前结束仍可给基于已作答内容的报告，同时说明未覆盖部分。

### 4.2 专项练习

**选择岗位与材料 → 选择题库题／薄弱项／原题，或填写备注进行 AI 定制 → 确认训练重点 → 选择交互方式 → 回答与有限追问 → 单题点评 → 再答一次或下一题 → 保存练习记录。**

从某场报告进入专项练习时，默认复用该场材料，开始前允许确认；不要求重新上传。针对原回答的重练保存为新尝试，不能覆盖正式模拟原分数，也不能把看过答案后的分数上涨直接描述为通用能力提升。

### 4.3 题量与操作默认值建议

| 项目 | 本次建议 | 状态 |
|---|---|---|
| 默认主问题 | 建议 6 道，正式模拟为 3 道题库＋3 道 AI；其他数量优先提供偶数选项 | 各半方向已确认，主问题统计与偶数数量为细则建议；6 道仍待试用 |
| 每道主问题追问 | 默认最多 1 次；有缺口才追，不强制每题追问 | 需试用调整 |
| 单次语音／视频回答 | 最长 120 秒，可提前结束 | 上限已确认；具体结束／提交交互为建议 |
| 重复问题 | 重新展示或播放，不记作新的主问题 | 建议 |
| 正式模拟重答 | 不在看过点评后替换原回答；从报告进入专项重练 | 建议 |
| 转写异常 | 保留录音，提供重新识别或核对入口；修订版注明来源 | 建议，不能静默改写原回答 |
| 中断恢复 | 返回原场次和当前题；已完成回答不丢，未保存片段如实提示 | 必须验证的质量要求 |
| 整场时间 | 依据题量、回答和追问给预计范围，不保证固定分钟数 | 建议；网络与分析等待单独展示 |

文字模式不受音频接口 120 秒上限约束。若以后增加限时压力训练，应作为明确的训练设置，不能把录音接口限制直接套到所有输入方式。

### 4.4 报告与长期记录

报告应包含本场岗位／材料、完成度、已覆盖能力、主要优势与待改进项、逐题原话依据及可执行建议。专业内容与表达结构分开，不从照片或画面推断能力。技术知识、项目深挖和行为题使用对应的评分依据。

第一版先支持从引用定位到回答文本、从问题进入本题录像；有可靠时间标记后再做精确秒点跳转，不能凭模型猜测生成时间戳。模型引用真实也不意味着结论正确，仍需审核题目和人工样例复评。

历史场次保留当时的简历、JD、题目和评价规则口径；后来修改资料不改变旧报告的含义。正式模拟与专项练习分开显示，画像按岗位、难度和评价口径组织，样本不足时明确说明。

## 5. 分阶段里程碑建议

阶段依据能力依赖安排，不设置固定周数，也不因课程截止而删除最终愿景。以下路线是本次设计建议，进入开发前再确认阶段出口。它优先减少反复修改，同时保证“全流程面试”尽早形成。

| 里程碑 | 用户能获得的结果 | 交付内容 | 阶段出口 |
|---|---|---|---|
| M0：产品设计确定 | 能清楚理解产品怎么玩、最终具备什么 | 目标人群、功能、页面职责、材料、反馈和录像规则、默认参数、阶段清单 | 关键方向无冲突；确认项和建议明确；当前停留本阶段，不开始项目代码 |
| M1：面试准备与个性化计划 | 能准备好一次与自己有关的面试 | 账户、简历解析核对、自备／内置 JD、匹配、审核样板题、AI 生成、各半配额与计划 | 材料缺失不能开始；计划来源各半且无重复；生成题有评价依据；无工作经历可用；计划可重开 |
| M2：完整文字模拟面试 | 能从准备到收尾完成一整场并得到报告 | 开场、混合来源主问题、两类题的有限追问、重复／跳过／暂停、收尾、证据报告、历史 | 指定材料完成整场；追问不冲掉主问题配额；反馈仅面后展示；报告关联来源与原回答；失败可恢复 |
| M3：完整语音面试 | 能听问题、录完回答并继续多轮对话 | 播题、录音、120 秒倒计时、转写、分析、语音追问与下一题、异常恢复 | 实际录音符合接口要求；播题不占答题时限；失败不丢已保存回答或重复推进 |
| M4：数字人视频面试与本地回放 | 能面对数字人完成整场，并逐题回看完整界面 | 两种预置视频、自拍小窗、每题画面与双方声音的本地保存、作答音频单独提交 | 回放确含数字人和本人小窗；戴耳机仍有题目声音；视频不上传；同题追问正确归组；保存失败有出口 |
| M5：专项训练与能力变化 | 能按需求定制或按报告补强，并观察同口径变化 | 专项入口、训练备注与重点确认、AI 定制题、逐题点评、同题新尝试、画像与历史对比 | 生成题落实允许的备注；冲突有提示；点评后可再练；不覆盖旧回答或混用不同口径 |
| M6：岗位覆盖与内容质量完善 | 能在更多计算机岗位获得有依据的训练 | 扩展并核验岗位 JD、题库、量表与追问；加强人工复评、体验和运行记录 | 每个开放岗位有对应审核内容与完整旅程；不只是改岗位标签；变更后核心流程回归通过 |

M1 做好共同的准备流程，M2 形成第一条完整面试闭环，M3／M4 在同一业务规则上扩展交互；M5 补全另一种训练场景和长期价值，M6 扩展内容。M2 内可以先用一题验证，再扩整场，但该阶段的出口仍是一场完整面试。

专项练习的部分能力在 M2 完成后已经可以准备，并非技术上必须等视频完成；若小组更重视训练价值，可以在保持共同规则的前提下调整 M4／M5 的先后。

每阶段都要覆盖必要的账号隔离、数据保存和错误状态，不将这些基础正确性全部推迟到最后。上述验收均是未来要求，目前尚未执行。

## 7. 与旧建议的关系

`整合方案/00–03` 保留调研、早期建议和经验来源，不作为已经确认的最终产品定义。出现冲突时，以用户最新明确决定为准。

已经明确需要替换的旧建议是：“临时上传视频到后端提取音轨”。当前用户要求本地录像、服务器只接收音频，因此该旧路径不再适用。

旧建议中的 Java 后端首岗、90 秒录音、按课程周数排期等，也不能覆盖本轮明确或仍待确定的产品规则。当前已确认采用每次回答 120 秒倒计时，时间由小组自主安排；首岗仍未选定。

旧建议中的“没有简历或 JD 也能开始”已被两份材料必需的要求取代；JD 可以选择内置模板。只录本人摄像头画面也不满足当前录像要求，必须以每题完整面试界面的回放能力验收。
