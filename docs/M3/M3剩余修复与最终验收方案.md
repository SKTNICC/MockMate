## 1. 目标、基线和边界

本轮是已有 M3 的修复与最终验收，不重新执行一套 V00–V09，也不新建语音原型。阶段目标仍为：手机播题→实际录音（最多 120 秒）→停止封存→上传/ASR→原始转写核对与修改→确认提交→最多一层追问→完整面试→有原话证据和答案来源的报告；异常和退出后恢复同一场、同一操作。

必须保留：M2 文字路径、旧场兼容、原计划/所有权/审核门槛/来源各半、严格 key+body 幂等、take/revision/worker lease fence、明确错误、追问 v2/评分 v3。修复只围绕 M3，不升级无关依赖，不改原材料/旧 Prompt，不放宽测试，不清业务库或手机数据，不部署或公开推送。契约有变更时先改 `tools/m1/build_contracts.py` 再同步生成物、两端、样例和回归。

## 4. R01：ASR/TTS 重试及当前 attempt 状态

落点：`backend/app/services/voice.py`、现有 jobs/worker；Android 重试/重播入口。

- 统一语音资产、转写与 job 当前 attempt 的状态投影。失败后 retry accepted 的 queued/running 必须立即可见，不再优先返回旧 failed 记录；最终 ready/empty/failed 回到当前 attempt 的结果。
- 保留原 job 的最大重试约束和持久身份。明确 TTS “重新播放”在 ready 时播放缓存、失败可重试时启动受控 retry、不可重试时给出原因；不得通过重复新建任务绕过预算。
- 事务和 worker 完成写入核对 attempt/lease、原 owner/session/turn/take/revision；旧重试、旧 take、重复 worker 完成不能覆盖新结果。查询和重复请求应保持并发安全。

回归：ASR timeout→retry 202→processing→ready；TTS 同链路；401/不可重试、429/超时、重试耗尽、旧 worker 迟到、重复点击。HTTP 故障在 test provider/受控桩制造，不能靠真实服务反复请求来制造失败。验收要同时验证状态、实际任务数/attempt 与前端能继续，不只检查 202。

## 5. R02：所有语音异步操作绑定原身份

落点：`ui/AppViewModel.kt` 的上传、转写、重试、播报、草稿加载与生命周期；沿用已有请求上下文和恢复机制，避免另建互相冲突的状态机。

- 定义一次操作的原 account、session、turn、take、voice revision 和导航/操作 generation。读取文件、请求、轮询、下载、播放器回调等挂起或异步返回后，都先核对原身份，再更新 UI、触发下一动作或呈现错误。
- 对成功与失败使用同样规则，尤其旧 401 不可清除新账号会话，旧错误不可把新页面切成 ERROR。
- 明确持有可取消的语音轮询 Job；离页/后台、退出、换场、重录、暂停/结束时正确失效，回到页面再按服务端真实状态恢复。不要仅在循环开头检查，也不要为躲竞态禁止正常导航。
- 播放 generation、录音 stop/finalize 与新 take 身份同步，旧焦点或播放回调不得启动、停止或修改新的题目资源。

回归：挂住 A 请求→切 B 场→释放 A ready/failed/401；同场重录新 take；换账号后旧回包；后台/前台恢复；暂停/结束后迟到。断言当前文本、阶段、账号、回合和资源均正确。

## 6. R03：未知上传回执与核对修改可持久恢复

落点：`core/audio/VoiceTakeStore.kt`、现有加密持久存储/写操作管线、`uploadVoiceTake`、`loadVoiceDraftFor`、提交与清理逻辑。

### 上传操作

- 首次网络发送前持久冻结完整有效请求：原 key、account/session/turn/take、session revision、expected voice revision、格式、摘要、长度和文件身份。后续重发不得改 body；失败落盘应明确报错，不先发送再假装已持久化。
- 返回丢失时，冷启动用原 key 原 body 重放，或可靠查询原成功资产/回执后继续原 ASR；当前草稿 revision 更新不能偷偷改掉原请求。不要仅增加重试次数。
- 已上传资产不能因本地文件还在就被当成“待新上传”；文件缺失/损坏不空文件重发，旧 take 不能覆盖新 take。
- 提交答案沿用原有幂等和事务冻结，确认 `asr/asr_corrected/text` 与实际提交内容、资产、转写 revision 一致。丢失答案 2xx 后不重复推进或重复回答。

### 核对草稿

- 原始转写与用户编辑内容分开；加密保存后者及匹配身份、版本、已编辑状态。相同资产重读、旋转/重建、后台或冷启动应恢复用户修改。
- 仅在对应提交被可靠确认或用户明确丢弃后清理。清理回调必须匹配原 take，不能误删随后录音或另一场草稿。
- 新 take/新转写版本不继承旧修改；退出/换账号遵循已有隔离与保留策略，不通过抹除所有草稿处理竞态。

回归：服务端提交 201 后丢回包→杀进程→新 ViewModel 冷启动→原上传确认并完成 ASR；已 ready 重进不覆盖修改；冷启动修改保留；新 take 不串；提交 2xx 丢失只产生一次答案；本地写失败、文件缺失及摘要损坏明确失败。

## 7. R04：TTS provider 缓存隔离

- `SpeechAsset` 模型唯一约束、insert 冲突目标、查询、job 输入摘要统一采用有效缓存输入，至少包括设计约定的 provider、文本摘要、音色、输出格式、adapter version 和现有作用域。
- 在 `b2c3d4e5f6a7` 后新增迁移，考虑旧资产和并发唯一性；不得改已执行的旧迁移来伪装升级成功。业务库升级前备份，先验证空库和旧 head 升级及数据保留。
- test/synthetic 标记必须保持真实；真实模式不能命中合成 provider 资产。相同 provider/内容仍复用，不增加不必要费用。

回归：同输入相同 provider 同资产；test→deepseek 使用不同资产；切回正确命中各自缓存；并发请求一项有效 job；无 Key/被禁用时明确失败；跨 owner 访问被拒。测试切换配置不执行真实网络调用。

## 8. R05：音频焦点、加密和中断封存

### 媒体中断

- 按 Android 明确的焦点枚举处理永久和临时丢失，语音不应在需要让出焦点时继续播放。停止、释放、错误提示及重新播放需与当前 generation 对应，不自动开始录音或提交。
- 核实录音的后台、音频资源不可用、来电/焦点及设备切换路径；保留已采样片段并标为 interrupted。不能将媒体焦点单元测试记为真实来电通过。

### 文件存储

- 落实原设计的成熟文件加密/Keystore、临时文件与原子封存；上传走受控流式解密并保持服务端要求的 PCM 摘要/长度/格式校验。不自造密文格式或把整个大音频塞入 Preferences。
- 录制中断或杀进程遗留临时内容可识别；恢复不把半截文件冒充完整已封存 take。完整性校验失败给明确错误，不静默删除可恢复资料。
- 兼容当前私有 PCM 草稿：明确安全迁移或识别策略，保留用户数据与原操作上下文，迁移失败可解释。任何存储格式变更需有版本和覆盖实际文件实现的测试。

验证：永久/临时焦点丢失及旧回调回归；真实文件加密、错误 key、密文破坏、缺失文件、写入中断、封存与清理、新旧草稿兼容。真机媒体与 120 秒实际行为在 R07 完成。

## 9. R06：隔离故障矩阵与完整 App 6 题

API 与 worker 必须共同指向隔离库和测试 provider；核对配置后再启动。不要仅修改 API 而让 worker 调到真实服务。保留当前业务进程，不误停其他代理或开发服务。

| 场景 | 必须观察的结果 |
|---|---|
| 上传 201 已入库但回包丢失 | 原 key/body 或回执确认，单一资产/有效 take，冷启可转写 |
| 答案 2xx 丢失，尚未刷新页面就杀进程 | 恢复原答案，恰好一次推进，无重复追问 |
| 核对修改后离页/冷启 | 同资产修改保留，新资产不串草稿 |
| 断网、重连、后台再回前台 | 任务状态可恢复，无后台无限轮询或自动录制 |
| ASR/TTS 401/429/timeout | 当前 attempt、可重试性和提示一致，受控次数，不无限重试 |
| TTS 断流、无 finish、错误完成码 | 不发布半文件，不误标 ready，不播放残片 |
| 旧 job/旧 take/旧页面迟到 | 不污染新结果、账号、当前媒体资源 |
| 暂停/退出/结束、权限拒绝、资源占用 | 保留合理草稿，明确原因，可显式文字作答 |

App 整场：6 主问、来源 3+3，通过真实页面入口完成播题、fixture 录制、停止、上传、ASR、编辑核对、确认、追问/下一题、收尾、报告及历史重开；断言原话引用与答案来源，使用合成内容时明确标识。此项是模拟器工程验收，仍不代表真实麦克风或评分质量。

模拟器：启动前记录既有设备/进程；只操作自己本轮创建的 serial。先核对设备，再配置并检查 `adb -s <serial> reverse`。默认 App 8000 对应 `reverse tcp:8000 tcp:8000`；隔离 8101 要对应实际 APK 地址，不能混用候选。使用 `try/finally` 关闭自身 emulator，验证 adb 与 emulator/qemu 进程不残留，清理自己添加的转发/临时 API/worker；不关闭用户其他设备或无关进程。

界面操作按当前全局约定委派指定 Terra 子代理；专用自动化/CLI 验证优先。若缺必要界面工具如实记录，不把日志退出码当作业务断言。

## 10. R07：真机、真实模型和正式内容

### 真机与真实语音

1. 连接后重新读取 serial，保留手机数据，不擅自卸载。先执行 `adb -s <serial> reverse tcp:8000 tcp:8000` 并检查映射，再进入 App；隔离端口则与 APK 配置一并记录。
2. 安装对应候选并实际说话，验证物理麦克风、停止/试听、ASR 原文、核对修改、来源提交、TTS 扬声器/耳机、权限拒绝/恢复、来电/失焦、切后台和真实 120 秒上限。120 秒测试计实际采样与时间，不用缩短 fixture 替代。
3. 完成受控真实 6 题、3+3 整场及报告/历史重开，逐步核对追问和评分证据。沿用既有受控小样本授权，优先虚构材料，事先限定场次与调用/重试预算；禁止批量、压力或无限重试。预算或真实材料授权不明确时仅暂停依赖步骤，先完成其他修复。
4. 每次记录 provider/model/adapter、请求数、成功/失败、request id、时长/用量与是否重试，脱敏日志。不得将 test 评分的合成报告记为真实质量验收，也不要求对已验证最小调用机械重跑来增加次数。

真实一场的 ASR/TTS/文字追问/评分会涉及多次请求；原三次调用只证明最小可用性。本方案的工程故障注入全部在隔离 provider 实施，避免额外真实费用。手机未连接时 R07 写“受阻：缺设备”，不能拖住 R01–R06。

### 正式内容 A25

检查题库和依据卡的来源、许可、审核资格、两名真实审核者及当前审核版本；服务端必须真实执行门槛、来源各半和去重。正式内容不足时记录缺少的具体条目/审查责任，不新建后台、不伪造双审、不把合成 fixture 改标为正式。可以分别报告“工程与真实语音通过、正式内容受阻”，但 M3 最终验收仍未通过。
