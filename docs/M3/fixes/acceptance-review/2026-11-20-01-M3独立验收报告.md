**M3 尚未达到阶段出口。** 已有端到端工程实现、通过的原有回归及历史模拟器证据；但新增探针复现了恢复、异步隔离、重试状态和缓存隔离问题。下一轮应先修复这些缺陷，再做故障、完整 App 整场和真机验收，不能只补一次麦克风演示便宣布完成。

## 3. 已复现缺陷

### F01 · P1：旧转写回包覆盖新场次

位置：`android/app/src/main/java/com/mockmate/app/ui/AppViewModel.kt`，`pollTranscript`（当前约 4043 行）。

复现：实际 `onVoiceRoomOpened` 启动 A 场转写查询，用 MockEngine 挂起该请求；将当前状态切到同账号 B 场并放入 B 的核对草稿；释放 A 的 ready 回包。`lateTranscriptCannotOverwriteAnotherSession` 预期保留 B 草稿，实际变为 A 原始转写，阶段进入 REVIEW。

原因：循环只在请求前检查 `RestoreScope` 与 `voicePollGeneration`，请求返回后直接写 UI。错误回包同样存在先写状态的问题。重试、上传前文件读取等相邻异步路径也需要按同一规则审查。

修复要求：原 account/session/turn/take/voice revision 与导航代次绑定；每次挂起操作返回后、每次 UI/媒体副作用前检查完整身份。离页、换场、换账号、重录、暂停或结束应让旧任务失效。成功、失败和迟到 401 分支都要覆盖。本轮动态复现的是同账号 A→B 场次切换，未动态验证跨账号回包。

### F02 · P1：核对修改在重读同一转写时丢失

位置：同文件 `updateVoiceReviewText`、`loadVoiceDraftFor`（约 4170、4260 行）。

复现：实际打开 ready 的 take，修改 `voiceReviewText` 为用户核对文本，再次调用同场 `onVoiceRoomOpened`。`reopeningSameReadyTakePreservesUnsubmittedCorrection` 预期保留修改，实际被 `transcript.text` 覆盖。

原因：用户修改只在内存；ready 草稿重读无条件覆盖。冷启动后丢失也有静态依据，但本轮动态探针仅覆盖同进程重读。

修复要求：持久化加密的核对草稿，绑定 account/session/turn/take/transcript revision；区分原始转写与用户编辑内容、已编辑状态。仅匹配当前上下文时恢复，确认同一提交成功或用户明确丢弃后清理，不修改服务端原始转写。

### F03 · P1：上传回执丢失后不能保证原请求恢复

位置：`core/audio/VoiceTakeStore.kt` 的 `VoiceTakeMeta`；`AppViewModel.uploadVoiceTake`（约 3885–3960 行）。

`VoiceTakeMeta` 持久保存 key、take、摘要等，却未保存首次上传的 session/voice revision 等完整请求上下文。上传时重新读取当前 `state.voiceDraft.voice_revision`，且绕过原有持久写操作管线。

探针 `test_cold_reopen_upload_preserves_original_request_context`：第一次 take K/key K/expected voice revision 0 上传返回 201；读取服务端草稿 revision 1；模拟当前客户端重建请求，用同 key K、同文件但 revision 1 重发，返回 **409 IDEMPOTENCY_CONFLICT**。这验证了丢失 201 后的恢复风险；不是在设备上实际杀进程的结果。

**服务端 409 正确，不能改成接受不同 body。** 客户端应冻结原始请求并原 key 原 body 恢复，或通过可靠回执/资产查询确认原上传成功后继续其 ASR。需要补实际 ViewModel 的“201 已提交但响应丢失→冷启动”回归，而非把本探针错误地改成服务端接受变更 body。

### F04 · P1：ASR/TTS 重试仍向客户端报告旧失败

位置：`backend/app/services/voice.py`，`_transcript_dto`、`_speech_dto`、`_ensure_speech_job`。

- `test_retry_asr_exposes_processing_instead_of_old_failure`：注入一次 ASR timeout，worker 持久记录失败；`POST /v1/jobs/{id}/retry` 返回 202、attempt 2 queued；立刻查询转写，仍为 failed/AI_TIMEOUT。旧失败行优先于新任务状态。
- `test_tts_retry_exposes_new_attempt_instead_of_old_failed_asset`：同样注入 TTS timeout，重试已 queued，查询资产仍为 failed。

Android 看到 terminal failed 会退出轮询；后端任务可能仍在运行。另据静态代码，重复请求播报会复用已有 failed job，界面“重新播放”不保证真正发起重试。

修复要求：查询状态反映当前有效 attempt；明确用户重试入口、预算和 attempt fence。旧 attempt 迟到结果不得覆盖新结果，不通过不断新建 job/资产重置重试上限。覆盖 queued/running/ready/failed/interrupted 及 worker lease 丢失。故障注入使用 test provider，不向付费服务制造错误请求。

### F05 · P2：TTS 缓存未按 provider 隔离

位置：`backend/app/models.py` 的 `SpeechAsset` 唯一约束；`voice.request_speech` 查询、冲突目标和缓存键。

探针 `test_tts_provider_change_does_not_reuse_synthetic_cache`：先生成 test provider 的 ready 资产，再把本次 settings 的 speech provider 切为 deepseek；再次请求相同片段返回同一 test 资产。新配置只参与请求，没有执行新任务或真实网络调用。

资产仍如实带 `provider=test`、`synthetic=true`，本轮没有发现把它改标为真实资产；问题是切到真实 provider 仍命中合成缓存，与设计规定的 provider 隔离不符。

修复要求：模型约束、查询、冲突目标与输入摘要统一包含 provider 等有效输入；新增迁移，不改已执行旧迁移。验证同 provider 复用、不同 provider 隔离、并发只建一个有效任务及历史数据升级。

## 4. 静态确认的设计差距

### F06 · P1：播放焦点丢失分支漏掉永久丢失

`core/audio/QuestionPlayer.kt:44` 使用 `change <= AUDIOFOCUS_LOSS_TRANSIENT`。Android 常量中永久 LOSS 为 -1，TRANSIENT 为 -2，因此永久丢失没有进入停止分支。依据：[Android AudioManager 官方定义](https://developer.android.com/reference/android/media/AudioManager#AUDIOFOCUS_LOSS)。

这是静态确认，尚未在真机复现。应明确处理所有需要停止的焦点丢失情况，检查旧焦点回调不会停止新播放；录音中断、来电和耳机切换仍需物理设备验收，不以单一 UI 后台回调替代。

### F07 · P2：录音文件加密与中断落盘未落实设计

设计要求见[阶段设计第 8 节](../../M3语音模拟面试开发交接.md)：成熟文件加密封装、Keystore、临时 `.part`、不可变封存和上传时流式解密。当前 `VoiceTakeStore` 只加密元数据，PCM 保存在 App 私有目录；`VoiceRecorder` 直接 `FileOutputStream(file)` 写最终文件，无临时文件提交边界。

App 私有目录提供访问隔离，但不等于实现了设计要求的文件加密。此项是代码与现有设计的差距，未发现或声称实际泄露。下一轮应实现既定存储约束，补录制中杀进程、缺失文件、密文损坏和完整性失败恢复；不自造加密协议、不空文件重发。
