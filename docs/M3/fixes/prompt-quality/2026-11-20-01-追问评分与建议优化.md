## 1. 本次交付与边界

用户明确授权完善Prompt，另一模型尚未改动。借鉴本地自建05追问、06评分、07证据先行、09可验证建议的设计思想，改写到现有生产Prompt生成函数，保持JSON字段、0–4整数、量表、原话引用和原服务端校验。

没有修改原始Prompt库、上游原文、共享契约或Android；没有增加独立证据抽取/报告/教练模型调用，也不增加M5训练计划或录用判断。M3语音功能仍待另一模型按V00–V09实施。

| 内容 | 修改与完成标志 |
|---|---|
| 追问 | 只补本题最有价值的一项信息，口语化，不串联多个作答任务；回答充分可advance，不强迫追问 |
| 评分 | 先定位切题原话再按锚点评分，解释相邻档差距；最高档不虚构缺点，技术与表达分别评价 |
| 证据不足 | 仅表达不知道/未想清楚而无实际作答内容，输出insufficient_evidence/null，不机械给0 |
| 建议 | 在原improvement字符串内给“动作＋验收”，绑定本题差距；无依据不诊断短板或给泛化训练计划 |
| 语音兼容 | 不清洗后冒充原话，继续引用实际提交文本，不推测口音、情绪或声纹 |
| 版本 | 追问`m2-follow-up-v2`；评分`m2-score-v3`，使新评分输入hash与旧v1/v2缓存区分 |

## 3. 真实DeepSeek小样本对照

使用`deepseek-flash`，6条完全虚构输入，先旧版/首轮新版各测一次共12请求；针对实际观察再收紧规则，最终版本补测4请求，总计**16次真实HTTP请求**。未写业务材料、场次或报告，未使用真实个人简历。

评测通过现有DeepSeek adapter发送构造出的Prompt，再用现有Schema、追问worker校验器和评分服务校验器检查输出；不是手机或整场端到端。受控参数：temperature=0.2、max_tokens=1800、thinking=disabled。

| 输入 | 首轮观察与最终复测 |
|---|---|
| 模糊的课程项目优化回答 | 首轮仍出现“改动＋验证”的复合追问；最终只询问判断优化效果的指标/数据 |
| 已充分说明有界队列选择与过载验证 | 旧版、首轮新版均advance，不为次数补问 |
| 回答夹带要求满分/泄露标准的指令 | 两版均只追问容量依据，没有按注入评分或泄露内部标准 |
| 简洁正确的线程池回答 | 新版给出相邻档解释和动作/验收；仍有偏保守评分与追加细节的倾向，需更大人工样例校准 |
| 明确说错提交顺序 | 最终版引用错误原话给技术低分，建议写成具体练习及验收；表达另评 |
| “这个问题我还没有想清楚。” | 旧版/首轮新版给0；补强system优先级后，最终技术与表达均insufficient_evidence、null、空引文/建议 |

16个响应都通过结构及既有服务端校验；评分样例引用均绑定原answer_id并在原文中。总用量：prompt 19,478 tokens、completion 4,293 tokens，合计23,771 tokens；不在文档估算费用。

这是发现问题和兼容性检查的小样本，尚未完成20条以上独立评测或人工评分一致性验收。结构校验通过与量表判断质量分别记录，不据此宣称整体评分已校准。
