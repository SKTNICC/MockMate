# MockMate M2 审查修复与真机复验指南

基线为 `52ed5ce`，2026-11-17。本文给接手修改的模型使用。产品行为和公开接口见 [M2 开发交接](../../M2文字模拟面试开发交接.md)，本文描述已实现版本中审查发现的八项修复。

基线复核通过后端 192 项测试、Android 72 项 JVM 测试、契约检查与 debug 构建。另在隔离 PostgreSQL 上复现了详情混读，并观察到评分任务只发送追问回答。其余问题来自对应代码路径的审查，需由执行者补复现或回归。当前本机 API 与 worker 已以 `AI_PROVIDER=deepseek`、`AI_MODEL=deepseek-flash` 重启，`/readyz` 显示数据库可用，启动核对未发起真实推理。

## 1. 执行顺序

| 顺序 | 编号 | 修复项 | 完成标志 |
| --- | --- | --- | --- |
| 1 | R1 · P1 | 迁移验证脚本可能删除已有库 | 同名直接失败，清理仅限本次创建的临时库 |
| 2 | R2 · P2 | 从面试间生成基础报告后页面卡住 | 一次点击即可展示已发布的基础报告 |
| 3 | R3 · P2 | 回答结果未知后，回到前台或刷新不能恢复 | 原 key 和原请求体重放成功，送达与未送达两种场景都能继续 |
| 4 | R4 · P2 | 同账号切页后，旧写入回包覆盖新页面 | 旧写入照常落库，新页面和草稿归属正确 |
| 5 | R5 · P2 | 并发追问发布时，详情混用旧阶段和新任务 | 对同一次详情响应，版本、回合、任务和允许操作一致 |
| 6 | R6 · P2 | 模型评分缺少追问题干 | worker 按回合发送题干与回答，旧评分缓存能正确失效 |
| 7 | R7 · P2 | 引文失效后仍显示基于该引文的建议 | 无效维度只发布受限状态和可解释的原因 |
| 8 | R8 · P3 | 点击证据时不定位原回答 | 概览和逐题引文都能定位到正确回合及对应文字 |

R2–R4 共用 Android 状态和操作恢复代码，按顺序改。R6–R7 一起跑评分缓存、报告发布与原话校验回归。先修 R1，再用迁移脚本验旧计划。完成全部后按第 5 节复验。

开始前运行 `git status --short` 和 `git log -1 --oneline`。如果已出现后续修改，先对照下方完成标志核实，再处理剩余缺口。当前工作区已有 `.gitignore` 改动，检查其来源和用途后保留用户改动。开发环境用本机已存在的 PostgreSQL，测试用经核对的独立 `mockmate_m2_test`。真实配置和密钥从本机读取。此次修复沿用 `/v1`、M1 确认计划、一次追问、配额和收尾发布规则。

## 2. 后端修改任务

### R1. 迁移验证只操作本次创建的库

**位置**：[verify_m2_migration.py](../../../../backend/scripts/verify_m2_migration.py)。重点检查 `main`、`_create_database`、`_drop_database` 和 `finally`。

**问题**：当前脚本默认用固定库名，也接受 `--database`。创建前先终止目标数据库连接并删库。误填现有开发库，或者默认库名已被其他运行占用，都会清掉原数据。核实这条路径时只用测试替身或预先创建的空白临时库。

**修改步骤**

1. 默认生成短随机后缀，例如 `mockmate_m2_migration_<随机十六进制>`。若保留 `--database`，只接受迁移专用前缀和合法长度，拒绝开发库、测试库及维护库名。确认管理连接和应用模板指向预期的同一本机实例，再派生临时库的应用 URL。
2. 创建只调用 `CREATE DATABASE`。同名库由数据库报冲突，脚本清晰退出。移除创建前的 `DROP DATABASE` 与连接终止逻辑。数据库名和角色名用 psycopg 的 `sql.Identifier`，值参数使用正常绑定。
3. 记录创建成功的库名。仅在本次创建成功且用户未传 `--keep` 时进入清理。关闭 TestClient、会话和 engine 后回收该库；失败时给出库名和可处理的信息。保留主验证异常，避免清理错误覆盖它。
4. 更新脚本帮助和引用说明。仍按「建立临时库 → 升到 M1 head `9b2c3d4e5f6a` → 写入并确认旧计划 → 升到当前 head → 用同一 plan ID 开场并完成一个追问任务」验证。

**回归**

- 用替身验证显式传开发库名时没有执行 DDL。模拟 `DuplicateDatabase` 时，没有调用删除或终止连接。
- 成功创建后，验证成功和中途抛错都只清理本次创建的库。`--keep` 返回时仍能连接该临时库。
- 脚本真实运行前确认管理连接只指向本机。检查升级后旧计划 ID、题序和材料绑定，确认开发库仍可从 API 读取。

### R5. 面试详情使用一致的读快照

**位置**：[interviews.py](../../../../backend/app/services/interviews.py) 的 `get_detail`、`build_detail`、`_allowed_actions`、`_job_summary` 与 `report_state`，[详情路由](../../../../backend/app/api/interviews_routes.py)，以及 [数据库会话配置](../../../../backend/app/core/db.py)。

**已复现**：GET 先读到旧会话的 `deciding_follow_up`。worker 随后提交追问为 `succeeded`。GET 再读问题、回合和任务，于是同一响应显示 `phase=deciding_follow_up`、`follow_up_job.state=succeeded`、`current_turn=null`，但 transcript 已包含追问。下一条独立 GET 才显示 `awaiting_answer` 和可答追问。

**修改步骤**

1. 所有详情字段从同一数据库快照生成。可在详情读取专用事务上从首条查询开始使用 PostgreSQL `REPEATABLE READ`，复用现有 engine 的连接池，也可用一个 SQL 语句完成一致投影。采用专用事务时，确保在读会话之前建立隔离级别。FastAPI 的鉴权查询可能已经在其 Session 里开始事务，不能在执行了查询后再给同一个事务改隔离级别。
2. 在该快照内读取带 owner 条件的 session、曝光回合、回答、job 和报告，进度、当前回合、允许操作都依这些值计算。报告就绪以已发布行存在为准。保持 401／404、公开字段白名单和原有端点。
3. 保持写入的行锁顺序。读取路径只做短事务，worker 对外请求模型仍在业务写事务之外。

**回归**：在 PostgreSQL 测试库用现有两题计划 helper 开场。提交一条会触发追问的主答，在详情读取 session 后、读取子表前，用独立 DB 会话执行 `worker.run_once()` 并提交。单次详情可以完整反映旧版本或新版本；不能混读。再做一次普通 GET，应看到最新追问。另测报告刚发布时，`report_state`、job 和 `allowed_actions` 一致。

### R6. 评分输入包含每个回合的题干

**位置**：[runner.py](../../../../backend/app/workers/runner.py) 的 `_handle_interview_report`，[prompts.py](../../../../backend/app/ai/prompts.py) 的 `score_prompt`，[interviews.py](../../../../backend/app/services/interviews.py) 的 `question_slot_hash`、收尾入队和报告发布。

**已复现**：截获评分 provider 调用后确认，两条追问记录只有 `answer_id`、`kind` 和 `text`。模型得到的题目对象只含主问题，无法判断「不会，因为……」回答的是哪一个追问。

**修改步骤**

1. 按实际曝光顺序整理同一主问题的回合。发送给评分 provider 的内部数据为每条有效作答保留 `answer_id`、`kind`、`prompt` 和 `text`。`prompt` 从实际保存的 `InterviewTurn.prompt` 读取。主问和追问一起评一次，跳过的追问没有有效回答。
2. 更新评分提示词，明确每条回答对应其题干，并要求引文通过 `answer_id` 关联原文。保留题目量表、可信度和独立表达维度。改的是 worker 内部输入，公开 Android DTO 沿用现有形状。
3. 升级 `SCORE_PROMPT_VERSION`。把实际题干与回合顺序、回答标识及原文摘要、评分口径和提示词版本纳入稳定的缓存 hash。worker 查缓存与发布事务重核必须使用同一计算规则。使用确定性的序列化，避免靠 Python 字典展示字符串拼接判断版本。
4. 已发布的旧报告仍可直接读。尚未发布的旧任务使用修复后的评分版本补评，旧 hash 的评分槽位不复用，原 job ID、尝试数和租约约束继续生效。保持原任务入队的输入标识稳定，发布时记录实际使用的评分提示词版本。有效同版本槽位仍可在任务重试时复用。

**回归**

- 用记录入参的假 provider 验证主答、追问各自带正确的 `prompt`、`answer_id` 和原文。加入「追问题意与主问不同，短答需借题干理解」的用例。
- 模拟旧版本评分槽位，确认当前 worker 会补评。再模拟同版本有效槽位，确认重试复用。验证已发布报告不改变 ID、分数和原始证据。
- 测试跳过追问、两类问题来源和零回答局。保留现有「零回答不发模型请求」和「追问不增加主问题数」断言。

### R7. 清除依赖失效引文的建议

**位置**：[interviews.py 的评分校验](../../../../backend/app/services/interviews.py)、[逐维度 UI](../../../../android/app/src/main/java/com/mockmate/app/ui/screens/InterviewScreens.kt)。

**问题**：`validate_question_score` 把非法引文对应维度降为 `uncertain`，清掉分数和引文，但仍沿用模型的 `improvement`。它可能基于被拒绝的引文，最终还会被 UI 当作可信的改进意见显示。

**修改步骤**

1. 在后端降级分支一并清掉 `improvement`，保留固定的「原回答无法定位引文」解释。空白或不可定位的引文同样处理。合法维度的原话与建议继续输出。
2. 复用评分校验覆盖槽位入库和报告发布。保持无效证据不进入整场优势／改进项。修复后生成的报告按此规则发布，已发布历史维持封存内容。

**回归**：用一条模型声称「用户用了未出现的框架」的引文及相关建议，验证发布报告的该维度为 `uncertain`、`score=null`、`evidence=[]`、`improvement=""`，无依赖该建议的概览项。加一条合法维度作对照，确认仍显示其建议。

## 3. Android 修改任务

修改入口主要在 [AppViewModel.kt](../../../../android/app/src/main/java/com/mockmate/app/ui/AppViewModel.kt)、[InterviewScreens.kt](../../../../android/app/src/main/java/com/mockmate/app/ui/screens/InterviewScreens.kt)、[操作存储和重放](../../../../android/app/src/main/java/com/mockmate/app/core/operation/OperationStore.kt)、[OperationReplay.kt](../../../../android/app/src/main/java/com/mockmate/app/data/OperationReplay.kt) 和 [JobWatch.kt](../../../../android/app/src/main/java/com/mockmate/app/data/JobWatch.kt)。

### R2. 生成基础报告后先跳转，再加载

**复现**：在独立测试环境让一个已结束、有回答的面试评分任务失败。在**面试间的收尾页**点「生成基础报告」。服务端成功创建报告，但回调先以旧页面上下文发出 GET，再 push 报告页。跳转后 GET 被归并闸门丢弃，报告页可能一直显示加载。

1. 在 `createBasicInterviewReport` 的成功分支核对原页面是否仍然有效。如果用户已离开，从其原场历史可正常查到报告。
2. 如果当前仍是该场面试间，直接复用 `openInterviewReport(sessionId)` 的「先 push，后加载」路径。如果已在该场报告页，保持现有页面，只刷新该场详情和报告。两个场景都结算本次操作的加载状态。
3. 无论创建成功、已被另一设备抢先创建，还是重试任务已入队，都从 GET 刷新服务端最终结果。依服务端提供的操作决定按钮，保留不同错误的提示。

**回归**：分别从收尾页和报告页触发。每次进入当前场正确报告、出现 `unscored` 与原答卷、加载遮罩消失。并发重复点击或再次打开时只存在一个 report ID。服务端失败时保留原页和可读问答，给出明确重试路径。

### R3. 回场和前台恢复都能重放待确认答复

**复现**：让代理接到 POST 后断开连接且本次未转发到 API，客户端无法确定送达。恢复网络，回前台、从历史重进原场或点刷新。当前实现只恢复 JobWatch 或查询详情，面试仍在原回合且提交被禁用。另用现有 `M1_TEST_DROP_RECEIPT_PATH` 测「服务端已提交，2xx 回执被丢弃」。故障注入仅在隔离合成环境执行。

1. 在当前账号的面试间恢复路径复用 `PendingOperationReplayer`。进场、回前台、用户点刷新或「确认提交结果」时，按当前场筛出待确认操作，先重放，再 GET 最新详情。维持既有 M1 冷启恢复入口。重放器若需要扩展，可加可选筛选条件和成功回执回调，默认行为继续兼容 M1。
2. 用原 `operationKey`、原序列化请求、原 `turn_id/revision` 重试。给同一账号同场的恢复入口做并发合并，手动与自动重试共享一次恢复。请求用原账号会话，持续断网时保留记录和醒目的手动重试入口。
3. 收到 `InterviewReceiptDto` 后识别对应回答和任务。真实回执或按回合核对一致后，清理匹配的 pending 与加密草稿。从新详情的 job 指针恢复唯一 JobWatch。冷启回执处理中也要能找到场次和相关任务，避免只支持直接返回 `JobDto` 的旧操作。
4. 若另一设备已提交不同回答或已结束该回合，刷新显示服务端状态，保留本机原草稿并给查看或复制出口。旧回合的稿件不能移到下一题。检查 Compose 的草稿保存效果，避免回合退出时把刚清理的已提交稿件重新写入。
5. 对可确定的拒绝显示对应错误并允许用户按最新状态操作；对仍不确定的结果保留原请求。网络恢复前无需反复自动发送。

**回归矩阵**

| 情况 | 预期 |
| --- | --- |
| 请求未落库，连接中断后返回前台 | 一次原 key 重放后保存，服务端只出现一份回答 |
| 已落库，丢了 2xx | 回放原回执，无追加回答、追问或评分任务 |
| 收到 2xx 后首次 GET 前杀进程 | 登录后能从详情恢复任务，仍是原场 |
| 另一设备已提交不同文本 | 展示已落库内容，原未提交稿可查看或复制 |
| 网络仍不可用 | pending 与加密草稿留存，可手动确认，无循环重试 |
| 恢复期间同号切场或 A 切 B | 旧回包只更新原账号原场记录，界面和提示不会串场 |

### R4. 原页面与原回合决定是否应用写入结果

**复现**：延迟计划 S1 的开始回包。点击开始后按系统返回，打开另一准备 S2，再释放 S1 回包。当前 `startInterviewForPlan` 只检查账号，会从 S2 跳回 S1。提交回答、跳过、暂停／继续、提前结束、追问失败继续、任务重试和基础报告也要核对。

1. 发请求前捕获账号、会话代数、导航代数、目标 plan 或 session，涉及作答时包含 turn 和 revision。优先复用 `RequestContext`、`RestoreScope` 及现有导航校验。
2. 将服务端回执与 UI 副作用分开。已确认回执、相关任务在原账号记录里正常完成。只有原页面和目标仍有效时，才更新当前场、加载提示、错误消息、草稿 UI、轮询或触发导航。回包后发 follow-up GET 时继续使用原目标，禁止在新的页面上下文中加载旧场次。
3. 同一场并行详情读取时，低 session revision 不能覆盖高 revision。同一个 job 的旧 attempt 或旧轮询结果也不能把已成功状态改回进行中。返回旧页面后重新读其当前服务端状态。
4. 进入新页面或换号时，旧操作的全局加载状态不应挡住新页面。401 仍使用现有账号代数判断，防止旧回包影响新登录。

**回归**：用受控延迟分别覆盖「S1 开场成功后用户已到 S2」、「旧场提交成功，当前场已有另一份草稿」、「旧错误到达另一场或另一账号」。核对原操作确实落库，当前页面的标题、对象、正文、提示与加载状态完全归属 S2 或 B。测试真实 ViewModel 调用路径，现有只测 `RestoreJobService` 的迟到用例不能代替写入回调测试。

### R8. 从证据跳到原回答

**复现**：打开有多题的长报告，在报告概览点一条后面题目的原话。现有点击只设置 `selectedAnswer`；题卡未出现在屏幕内时看不到变化。

1. 给报告的 `LazyColumn` 接入 `LazyListState`。按实际显示的列表项建立 `answer_id → 题卡项` 对应，处理「优势／改进项」等可选卡片带来的偏移。
2. 概览引用和逐维度引用使用同一个跳转逻辑。携带 `answer_id` 与 `quote`，先移动到对应题卡，再让指定主答或追问可见。用原始正文的子串位置高亮引文，兼容换行、中文和表情。相同引文重复出现可定位首个匹配。
3. 旧报告的目标回答或片段缺失时，提示无法定位并保留报告可阅读。详情只显示当前报告中的对应题目与回答，保持现有账号归属校验。

**回归**：用含可选概览卡的长报告点击最后一题的追问引文，核对滚动、回合和高亮文本。从逐题维度再点另一条证据，确认不会停留在旧回答。检查引用含中文标点、换行和 emoji 的样例。

## 5. 真机与 DeepSeek 复验

### 5.1 真机故障路径

1. 在隔离合成环境核对 debug 包的签名与测试端点。使用 `adb install -r` 并指定真机。当前 APK 访问手机侧 `127.0.0.1:8000`，若合成 API 开在电脑 8001，可用 `adb -s <真机序列号> reverse tcp:8000 tcp:8001`。先用 `reverse --list` 检查原映射并记录，做完合成验证恢复电脑 8000 的映射。若签名冲突，保留手机内已有数据。具体步骤见 [Android 真机联调](../../../../android/README.md)。
2. 在同一候选包上，用合成账号从确认计划完成一整场六题。至少覆盖题库、生成题两类追问，核对六道主问题来源 3＋3。记录报告里的计划数、已答数、追问数并点击定位一条追问原话。
3. 另开合成场次依次测试掉回执、网络恢复、暂停后冷启、另一设备写入、同号切场和 A/B 迟到。再测评分失败后从收尾页生成基础报告。使用真实中文 IME 选词，输入包含换行与 emoji 的回答。

### 5.2 验证真实 DeepSeek

1. 保持模型请求由后端 worker 发出。当前本机配置需让 API 与 worker 均从同一后端配置读取 `AI_PROVIDER=deepseek`、`AI_BASE_URL=https://api.deepseek.com`、`AI_MODEL=deepseek-flash` 和已有 Key。升级源码之后重启 API 与 worker。启动检查核对 `/healthz`、`/readyz` 和 worker 已启动；模型调用结果从业务任务观察。[当前接入方式](../../../../backend/README.md) · [DeepSeek Chat Completions](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)
2. 真机恢复 `adb reverse tcp:8000 tcp:8000`，用一份合成简历和 JD 新建两题计划。记录一次真实匹配／出题、一次主答后的追问判定和一次面后报告。真实模型允许正常决定无需追问；要检验 R6 时，用需要补充理由或边界的合成主答获得追问，再比较题干、回答与模型评分。日志证据用 provider、model、请求 ID、任务状态和用量字段，排除 API Key、token、完整材料和回答。
3. 核对样板提示。计划页与面试间目前依据样板标记显示「测试 provider」，而该标记表示样板岗位，开启 DeepSeek 后依然可能为真。把两处文案改为说明「开发样板岗位与题库，仅用于联调」，并以服务端任务记录验证实际 provider。为此无需给现有公开响应增加字段。[计划页](../../../../android/app/src/main/java/com/mockmate/app/ui/screens/PlanScreens.kt) · [面试间](../../../../android/app/src/main/java/com/mockmate/app/ui/screens/InterviewScreens.kt)
4. M2 的真实评分由人工抽查一到两题，核对引用是否逐字出现、追问评分依据是否契合题意、证据不足时是否降级。合成样板加真实模型说明调用已跑通；正式岗位验收关闭样板和 fixture 开关并使用审核内容，按原阶段出口验证六题。
5. 若失败，先查看 job 错误码。`AI_AUTH_FAILED` 核对 Key，`AI_RATE_LIMITED` 核对额度与请求频率，`AI_TIMEOUT` 检查延迟，`AI_INVALID_OUTPUT` 核对结构、空内容、截断和业务校验。服务端现有 `response_format=json_object` 需要保留。若真实验证出现默认思考模式造成明显延时、费用或响应异常，再在 DeepSeek adapter 中试验明确的 `thinking.type=disabled` 与适合该任务的输出上限。先用模拟 HTTP 验证 payload，再对比真实样例，避免把模型配置调整混进功能修复验收。[思考模式](https://api-docs.deepseek.com/guides/thinking_mode/) · [JSON 输出](https://api-docs.deepseek.com/zh-cn/guides/json_mode/)
