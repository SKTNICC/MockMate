## 1. 消除面试详情的嵌套数据库取连接

### 现象与定位

`GET /v1/interviews/{session_id}` 先通过 `get_current_session` 和 `get_current_user` 完成鉴权。鉴权查询使请求的 SQLAlchemy Session 持有一条连接。随后 `get_detail` 通过 `read_snapshot_session` 从同一个池再取一条连接。池被并发鉴权占满时，请求都在等待第二条连接，直到池超时。复审在真实 PostgreSQL 上用两条池连接模拟此过程，让两个并发读操作各保留一条连接，再调用快照函数，两次均触发池超时。[数据库会话](../../../../backend/app/core/db.py#L45) · [鉴权依赖](../../../../backend/app/api/deps.py#L25) · [详情路由](../../../../backend/app/api/interviews_routes.py#L127) · [详情服务](../../../../backend/app/services/interviews.py#L522)

### 实施步骤

1. 建议采用最小改动方案。在详情路由确认 `db` 与鉴权链使用 FastAPI 默认缓存的同一个 `Depends(get_db)`。先解析场次 UUID，再把 `user.id` 复制到普通变量，使用 `db.rollback()` 结束该 GET 的鉴权只读事务并归还连接。随后将已保存的 `owner_id` 传给详情服务。回滚可能使 ORM 对象过期，之后的路由、响应构建与日志都使用已经捕获的普通值，避免访问 `user` 触发再次查询。把这一步限定在详情 GET，核对该路径的鉴权依赖没有需要提交的写入。
2. 另一种可行实现是为详情 GET 建立单独的请求级只读 Session 依赖。鉴权查询和详情查询必须明确使用同一个 Session，`get_detail` 也应直接使用该 Session。事务在第一次查询前设置 `REPEATABLE READ` 与只读，依赖在请求结束时释放。采用此方案时，复用现有鉴权校验和错误语义，避免重复实现令牌校验。
3. 保留详情内部的归属查询。会话头、当前回合、问答、任务摘要和报告状态仍在同一快照内读取。保留 401、404 及既有响应字段。连接池大小不需要调整。执行前查找 `get_detail` 的全部调用方，再决定是否清理旧的可选 `db` 参数。

### 回归与验收

- 路由级并发回归使用隔离 PostgreSQL 与独立测试 Engine，配置 `pool_size=2`、`max_overflow=0` 和短超时。使用两个已登录请求读取详情，在鉴权完成、详情开始前用有界屏障对齐。旧代码可稳定触发池超时，修复后两个响应均为 200，重复运行时连接能归还。测试中的屏障放在允许两个鉴权请求都抵达的位置。测试若采用单请求单连接的方案，也可用池大小为 1 的认证详情请求覆盖串行自阻塞，再用两并发补测。
- 保留现有 `test_detail_uses_one_read_snapshot_when_worker_commits_mid_read`，验证 worker 在子表读取期间提交后，响应内部状态仍匹配，下一次 GET 才能完整看到新状态。追加或运行既有的无凭证、跨账号、非法 UUID 检查。[面试 API 测试](../../../../backend/tests/test_interviews.py#L584)

## 2. 切场后丢弃迟到的 Android 详情更新

### 复现

打开面试 A，发起详情刷新。让详情 GET 返回并通过页面校验，再卡住 `operations.pendingFor` 的本地读取。导航到面试 B，等待 B 加载，再放行 A 的读取。当前 A 的协程可能覆盖全局 `interviewDetail`、待确认回合或草稿状态，也可能把 B 的加载状态清掉。前台详情刷新、后台刷新以及预读待确认回合都有同类的挂起窗口。[前台刷新](../../../../android/app/src/main/java/com/mockmate/app/ui/AppViewModel.kt#L1583) · [后台刷新](../../../../android/app/src/main/java/com/mockmate/app/ui/AppViewModel.kt#L2626) · [待确认存储读取](../../../../android/app/src/main/java/com/mockmate/app/core/operation/OperationStore.kt#L419)

### 实施步骤

1. 发起刷新时捕获页面身份与目标场次。沿用 `pageSnapshot()` 和 `isScopeCurrent(page)`，覆盖账号、登录代次、导航代次、页面种类和场次。后台刷新入口也核对传入的 `sessionId` 属于捕获的页面。相同场次的新导航代次是不同页面。
2. 逐段检查 `refreshInterviewSession`、`fetchInterviewAndOptionalReport`、`refreshInterviewInBackground`。在 `recoverInterviewSession`、网络 GET、`pendingFor` 等挂起点返回后，紧贴下一次 UI 更新重新校验页面，尤其是写入 `pendingInterviewTurnId`、调用 `applyInterviewDetail`、清除加载提示及启动轮询前。保持现有版本比较，防止同一场次的旧 revision 覆盖新详情。
3. 将 `recoverInterviewSession` 的 UI 提示关联到原页面快照，或让它返回恢复结果，由仍处于原页面的调用方展示。当前按场次判断的 `isInterviewPage(sessionId)` 会放过离开后又返回同场的旧协程。原账号操作回执可以继续按原键完成持久化。新页面的提示、导航、加载和草稿展示仍须通过其自己的页面校验。
4. 将最终校验和紧随其后的状态更新放在同一个主线程执行片段，中间没有挂起调用。注意 `applyInterviewDetail` 即使收到的 `detail.session_id` 等于原请求 ID，也还需要保证当前页面仍是本次请求的页面。

### 回归与验收

- 通过 ViewModel 的正常入口触发刷新，用 `CompletableDeferred` 或受控测试调度器阻塞本地 IO。分别覆盖初次读取待确认回合、详情成功后的本地读取和后台刷新。切到 B 后释放 A，并断言 B 的详情、待确认回合、草稿、加载提示与消息归属 B；A 的迟到结果不触发新轮询。
- 补测从 A 离开再打开 A、从 A 的面试间切到报告页，以及在读取期间退出并切到另一个账号。保留同页新旧 revision 乱序用例。测试要穿过挂起点和最终写入，单独验证合并规则会漏掉本缺陷。[现有 Android 回归测试](../../../../android/app/src/test/java/com/mockmate/app/M2ReviewFixTest.kt)

## 3. 让任务重试按所属面试场次恢复

### 复现

让某场追问或评分任务进入允许重试的失败状态。点「重试」，在客户端保存待确认操作后、服务器收到请求前断网。恢复网络后回到前台、重新进入原场或手动刷新。当前记录的 `targetId` 是 `jobId`，而场次恢复按 `sessionId` 筛选，所以原请求不会被该入口重放。[重试入口](../../../../android/app/src/main/java/com/mockmate/app/ui/AppViewModel.kt#L2049) · [场次恢复与筛选](../../../../android/app/src/main/java/com/mockmate/app/ui/AppViewModel.kt#L1706) · [重放执行器](../../../../android/app/src/main/java/com/mockmate/app/data/OperationReplay.kt#L160)

### 实施步骤

1. 为待确认操作增加带默认值的可空场次元数据，例如 `interviewSessionId: String? = null`，从 `retryInterviewJob` 经 `performWrite` 和 `OperationCoordinator.prepare` 持久化到 `PendingOperation`。继续用 `targetId=jobId` 构建重试 URL，用 `RetryJobPayload(expectedAttempt)` 构建原请求。
2. 将新字段作为本地路由元数据。保持原 payload 序列化、`bodyHash`、重试 HTTP 请求体和幂等键匹配规则。当前协调器会复用已有记录。若找到同一条旧记录但缺少场次元数据，在账号锁内补齐并保留其旧键；写入失败沿用存储错误路径。旧操作应仍能被冷启动全量恢复读取。
3. 当前场恢复时优先匹配新元数据。为旧版面试重试记录提供兼容分支，使用当前场服务端详情中确认为本场的 `follow_up_job.id` 和 `report_job.id`。必要时在本场恢复前先读取一次详情，再执行已确认归属的重放，随后重新 GET 获取最终状态。当前详情无法确定归属时，保留原记录，由既有账号级全量恢复或后续可确认的本场恢复处理。M1 的 `retryJob` 继续由原有路径处理。
4. 重放使用同一账号、同一 `jobId`、原 `expectedAttempt` 和原 `Idempotency-Key`。成功后保留现有 active job 记录逻辑，并在页面仍有效时刷新当前场、恢复轮询。结果仍不确定时保留待确认记录。确定拒绝时沿用现有拒绝处理并以最新详情展示可用操作。将同场并发刷新纳入现有恢复互斥，验证没有并行重发。

### 回归与验收

- 覆盖 `follow_up` 与 `interview_report` 两种任务。模拟请求从未到达服务器，重进本场或回前台会重放并只增加一次 attempt。再模拟服务器已入队但客户端没收到响应，重放得到原回执，服务端 attempt 保持原值。记录测试中的请求次数及幂等键是否相等。
- 同账号同时保存 A、B 两场和 M1 的待重试操作，恢复 A 时只发送已确认属于 A 的重试。模拟连续刷新和两次不确定响应，确认保留旧键，最终成功后移除待确认记录。
- 从旧 JSON 装载不含场次字段的待确认重试，核对本场任务 ID 匹配、全量恢复和再次手动重试均沿用旧键。测试需要经过真实的记录准备、筛选和重放路径。[本地操作存储](../../../../android/app/src/main/java/com/mockmate/app/core/operation/OperationStore.kt#L175) · [已有恢复回归](../../../../android/app/src/test/java/com/mockmate/app/M2ReviewFixTest.kt)

## 4. 让报告证据滚到具体引文所在行

### 复现

用含多题、长答案的报告，从「优势」或「待改进」点击最后一题追问末尾的引文。当前能找到正确题卡并高亮原文，但 `BringIntoViewRequester` 绑定的是整块回答。回答很长时，屏幕可能停在回答开头。当前题卡滚动和回答定位之间还依赖固定的 60 毫秒等待。[报告跳转](../../../../android/app/src/main/java/com/mockmate/app/ui/screens/InterviewScreens.kt#L596) · [精确子串查找](../../../../android/app/src/main/java/com/mockmate/app/ui/screens/InterviewReportNavigation.kt#L36)

### 实施步骤

1. 保留题卡索引和 `quoteRange`。概览与维度引用统一传入 `answerId` 和 `quote`。每次点击生成一个可区分的跳转请求，先让 `LazyColumn` 滚到对应题卡。
2. 把 `BringIntoViewRequester` 绑定到目标回答的 `Text`，收集该 Text 的 `onTextLayout` 结果。等本次选中的答案已经挂载、完成布局并拥有有效的 `TextLayoutResult` 后再执行第二段滚动。可以用绑定目标 Text 的布局回调和 `LaunchedEffect` 协作。删除以固定时长猜测布局完成的逻辑。
3. 将 `quoteRange` 的字符串偏移映射为实际行号。可以使用 `getLineForOffset`、`getLineTop` 和 `getLineBottom` 得到文本局部坐标中的行矩形，再把这个矩形传给 `bringIntoView(rect)`。优先保证引文起始行可见。引文跨行且整体能放入视口时，可合并对应行的范围。让矩形与 requester 使用同一个节点的坐标系。高亮仍使用原字符串的精确范围，并沿用重复引文取首个匹配的规则。
4. 框定跳转的生命周期。连续点击时只执行最新目标，离开报告后结束旧滚动。遇到旧报告缺少原回答时显示已有提示。能找到回答但找不到原句时，可定位到回答并提示精确引文缺失。保留 report 中已有题卡、覆盖度和证据显示逻辑。

### 回归与验收

- 构造至少多屏的长回答，把唯一引文放在末尾。点击概览证据，检查视口中实际出现被高亮的文字，不能只用题卡进入组合或节点存在作为通过条件。用固定窄视口和适当字体大小稳定复现换行。
- 从逐维度证据跳到另一段答案，快速交替点击，并重复点击同一证据。验证最终位置和高亮对应最后一次点击。补查中文标点、换行、emoji、重复字串和缺失引文。
- 沿用现有 Compose 测试依赖，优先跑可用的真机或模拟器。可以通过测试语义或布局坐标断言引文行与视口相交，或用实际截图确认。单元测试保留题卡索引与字符串范围断言，界面测试单独记录实际滚动结果。[现有范围测试](../../../../android/app/src/test/java/com/mockmate/app/M2ReviewFixTest.kt#L320) · [设备测试入口](../../../../android/app/src/androidTest/java/com/mockmate/app/M2EntryDeviceTest.kt)
