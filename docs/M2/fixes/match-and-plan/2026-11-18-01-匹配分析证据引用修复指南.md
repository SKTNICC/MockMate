# MockMate 匹配分析证据引用修复指南

修复确认简历和 JD 后，「匹配分析」因模型引用错条目而失败的问题。模型只选择已保存的简历条目 ID，后端根据 ID 组装证据并继续执行原有校验。为同一版本的失败匹配任务开放现有的显式重试入口，App 根据服务端状态展示可用操作。

编写本指南时 HEAD 为 `fca82f6`。实施前运行 `git status --short` 和 `git log -1 --oneline`，保留现有 UI、报错面板、技能选择器和 M2 行为。这次改动涉及匹配分析的模型输出、任务判断与匹配页面提示。

## 一、已确认的根因

本地开发库的任务记录显示，DeepSeek 已返回匹配结果。模型把一段确实出现于整份简历的文字归给 `skill-1`，但这段文字没有出现在 `skill-1` 自己保存的 `evidence.quote` 里。我用实际快照和同一个校验函数离线复现了失败，并确认该条目自身的证据通过。任务为 `match`、第 1 次尝试、材料所属准备版本为 4，失败码为 `AI_INVALID_OUTPUT`，没有发布报告。

现有 prompt 让模型同时返回 `snapshot_id`、`item_id` 和自由填写的 `quote`，只明确限制引文必须来自整份简历，条目 ID 必须存在。后端还检查引文逐字属于指定条目的证据。这道校验应保留，它防止把材料中的一段文字归给无关条目。UI 这一轮多展示了底层错误，匹配失败发生在 Worker 的证据校验阶段。[现有匹配提示词](../../../../backend/app/ai/prompts.py#L123) · [证据校验](../../../../backend/app/services/evidence.py#L37) · [匹配 Worker](../../../../backend/app/workers/runner.py#L395)

## 二、让模型只选择证据条目 ID

### 2.1 模型输出契约

在 AI 层定义专用的内部结果，例如 `MatchSelectionOutput`。使用现有 Pydantic 严格模型风格，拒绝未知字段。每项仍有 `requirement_id`、`status`、`explanation` 和 `suggested_focus`，证据字段改为 `resume_item_ids`，类型为字符串数组。显式要求数组字段存在，无证据时传空数组。

```json
{
  "rows": [
    {
      "requirement_id": "req-1",
      "status": "supported",
      "resume_item_ids": ["project-1"],
      "explanation": "已确认的项目条目描述了 Java 集合的使用。",
      "suggested_focus": "说明为什么选择这种集合，以及如何验证边界。"
    }
  ]
}
```

这个形状只用于 DeepSeek 响应解析。对 App 和下游计划服务，继续返回现有 `MatchRow.resume_evidence`，其中每条仍是 `Anchor(snapshot_id, item_id, quote)`。旧报告继续按现有格式读取。现有 `MatchRow`、数据库记录和 OpenAPI 可沿用，无需为内部模型输出建立公开 API。[公开报告结构](../../../../backend/app/schemas.py#L271) · [DeepSeek 适配入口](../../../../backend/app/ai/provider.py#L816)

### 2.2 组装候选并更新 prompt

1. 从本次绑定的已确认简历快照构造候选表。复用 `profile_items`，每个候选包含原有 `item_id`、供模型理解的条目信息和该条目的已保存证据。使用非空、逐字存在于快照原文的证据作为可引用候选。模型看到的候选列表与后端生成证据时使用的候选表应来自同一次构建。
2. 修改 `match_prompt`，提供真实 JD 要求 ID 和简历候选 ID，明确模型的任务是为每条 JD 要求找出与之相关的候选。列出的引文只供模型理解，输出只包含候选 ID。更新提示和 JSON 示例里旧的 `anchors.item_id`、`snapshot_id` 和 `quote`。可保留整份已授权简历原文作语境，同时在提示中说明可引用证据以候选表为准。
3. 要求每个 JD 要求出现且只出现一次。只有确有直接支持时才选 `supported`，且至少选一个候选；相关但证据不充分时用 `to_verify`；`not_evidenced` 使用空数组。未体现和待验证不等同于候选人不具备能力。解释和建议只基于材料与岗位要求。

### 2.3 在适配器组装证据并校验

1. 在 `DeepSeekProvider.match_requirements` 用现有 `_chat_json` 和 `_validate` 解析新的内部 DTO，再根据 `resume_item_ids` 查候选。每个有效 ID 得到一条完整 `Anchor`，`snapshot_id` 取本次简历快照的 ID，`item_id` 取已选的条目 ID，`quote` 逐字使用该条目保存的 `evidence.quote`。保留现有 `AiProvider.match_requirements` 返回 `list[dict]` 的统一形状，测试 provider 和 Worker 可继续沿用。
2. 模型返回未知 ID、不可引用条目、重复证据 ID、`supported` 无证据、`not_evidenced` 附带证据，或 JD 要求缺失、重复时，走受控的 `AI_INVALID_OUTPUT`。可给新错误附 `stage=match`、`reason=invalid_evidence_selection` 与条目或要求 ID 等诊断字段。未知 ID 不通过猜测或模糊匹配纠正，也不替模型把无证据结论改成支持。
3. 保留 Worker 里的 `validate_match_rows` 与 `validate_anchor`，继续验证报告覆盖所有 JD 要求、材料归属、条目归属和原文证据。保留发布报告前的准备版本、快照和任务租约校验。控制错误仍使用现有任务失败和调用记录流程。诊断可记录 ID、原因和调用状态，避免新增原始简历、提示词或完整模型输出日志。[适配器的模型校验](../../../../backend/app/ai/provider.py#L91) · [报告发布路径](../../../../backend/app/workers/runner.py#L418)

## 三、给当前版本的失败任务一次显式重试

当前同一准备、任务种类和输入版本最多对应一条任务。反复点「开始匹配分析」会拿回相同任务。原 `is_retryable` 对 `match` 的 `AI_INVALID_OUTPUT` 不放行，因此旧失败任务无法使用「重试」。[任务复用](../../../../backend/app/services/jobs.py#L133) · [重试资格](../../../../backend/app/services/jobs.py#L232)

1. 在 `is_retryable` 中为 `kind=match` 放行 `AI_INVALID_OUTPUT`，复用已有的终态、次数上限、当前输入版本与归属检查。继续使用 `POST /v1/jobs/{job_id}/retry` 和 `expected_attempt`，沿用幂等机制和并发锁。默认最多两次尝试，第 1 次失败时剩一次。其它任务的现有重试规则保持。
2. 资格是读任务时动态计算的。部署后，仍对应当前准备版本且次数未用尽的旧失败任务，查询状态就能返回 `retryable=true`。由用户明确点击重试，再用同一任务 ID 排队并增加 attempt。保持现有授权范围，不在刷新、重开页面或服务重启时自动调用模型。
3. 材料换绑或准备版本变化时，旧任务继续不可重试。用户用新版本发起匹配时走正常创建任务路径。重试过程中材料再变更时，旧结果不能写进新版本。API 更新后需同时重启 Worker，避免新版 API 允许重试而旧 Worker 仍用旧 prompt。[重试路由](../../../../backend/app/api/jobs_routes.py#L44) · [匹配任务输入](../../../../backend/app/services/preparations.py#L238)

## 四、让 Android 提示匹配实际状态

1. 在 `ErrorDiagnosticsMapper` 为匹配证据错误添加具体文案，建议「本次分析未能把引用关联到正确的简历条目。本次匹配报告未生成，已确认的材料已保留。」优先使用结构化错误原因，兼容旧任务时用 `kind=match` 和原有的「引用原文不属于所引用的材料条目」识别。可从 `fromJob` 显式传递任务种类，避免按展示用的 Context 文本解析。沿用详细诊断面板。[错误映射](../../../../android/app/src/main/java/com/mockmate/app/ui/ErrorDiagnostics.kt#L45)
2. 当服务端 `retryable=true` 时，文案提示「重试匹配分析」，按钮沿用 `retryCurrentJob` 的正常调用、轮询和恢复路径。提示用户重试会再次调用模型。当为 false 时，不提示点击重试。当前版本的失败任务存在时，避免把那个只会复用失败任务的「开始匹配分析」显示成可用的重试入口。旧版本失败结果不应该挡住新版本的「开始匹配分析」。[匹配页面](../../../../android/app/src/main/java/com/mockmate/app/ui/screens/PlanScreens.kt#L60) · [任务恢复按钮](../../../../android/app/src/main/java/com/mockmate/app/ui/components/Common.kt#L565) · [重试入口](../../../../android/app/src/main/java/com/mockmate/app/ui/AppViewModel.kt#L1655)
3. 保留「只读查询最新状态」，它用于升级后刷新旧任务的重试资格。报告未发布时显示失败和合适的操作。模型证据归属失败时，通用提示无需要求用户丰富简历或 JD；只有服务端给出了材料缺失或待确认等明确原因，再引导修改材料。

## 五、回归与交付

| 场景 | 验收条件 |
|---|---|
| 截图问题的合成复现 | 构造两条简历条目，让某句文字只出现在整份原文的其它位置。原 `validate_anchor` 仍拒绝把它挂到错误条目。模拟 DeepSeek 仅返回合适的 ID，后端使用该条目已保存的原文生成报告，证据校验通过。 |
| 输出异常 | 模拟不存在的 ID、过去的自由引文字段、重复证据 ID、缺失或重复 JD 要求、两种状态与证据数量矛盾。错误可诊断，匹配报告未发布，准备中没有错误报告 ID。 |
| 公开格式 | 模拟 HTTP 验证请求要求输出 ID，且 adapter 返回的公开证据仍有正确的快照 ID、条目 ID 和原文。旧报告可读，现有匹配后生成计划的端到端测试通过。 |
| 旧任务恢复 | 预置第 1 次失败、旧错误消息、准备版本仍当前的任务。GET 返回可重试。只读查询和重复开始不会再次调用模型。一次显式操作用原任务 ID 加到第 2 次，正常生成报告或按错误结果停止。超过上限、输入过期和其他账号的任务不能重试。 |
| Android 文案与操作 | 覆盖旧错误及结构化新错误，分别校验有资格和无资格时的文案与按钮。点击重试实际走已有重试接口。旧准备版本结果晚到时，当前页面和报告不被覆盖。 |

先扩展已有的 [AI adapter 测试](../../../../backend/tests/test_ai_adapter.py#L137)、[模拟 DeepSeek 的匹配与计划测试](../../../../backend/tests/test_deepseek_flow.py#L177)、[证据规则测试](../../../../backend/tests/test_evidence_rules.py) 以及 [任务重试测试](../../../../backend/tests/test_jobs.py)。模拟 HTTP fixture 原来会从 prompt 解析 `snapshot_id` 并拼引文，更新为返回候选 ID，再用现有报告 API 断言证据。Android 增加针对匹配错误的文案或 ViewModel 回归。

确认测试终端指向隔离 PostgreSQL 库后，在仓库根目录进入 `backend` 运行。测试库会重建 schema。本地开发的默认联调库和测试库的用途见[本地开发说明](../../../overview/本地开发.md)。

## 可复制给执行模型

> 按《MockMate 匹配分析证据引用修复指南》在当前工作区完成修复。DeepSeek 匹配只选已保存的证据条目 ID，服务端组装逐字原文并保留现有校验与公开报告格式。让当前输入版本的失败匹配任务使用已有的限次显式重试，并让 App 文案与服务端资格一致。覆盖旧误引复现、无效 ID、旧任务重试和现有计划流程，执行回归并报告实际结果。
