# MockMate 计划槽位缓存跨版本兼容修复指南

这份指南只处理上一轮复查发现的 **P2 缓存兼容问题**。目标是在当前准备版本的任务仍有合法重试资格时，升级前通过校验的 AI 题也能复用。后续槽位仍收到已考察摘要。保留已实现的重复题纠正、任务次数限制和三加三配额。[上一轮重复题修复指南](2026-11-18-03-生成计划重复题修复与续跑指南.md)

## 一、根因与影响

Worker 按槽位构造生成上下文，把整个字典算成 `context_hash`，再和 `job_work_items` 保存的摘要比较。这轮给上下文新增了 `previous_summaries`，用来提示模型前序题的考察点。旧版没有这个字段。哪怕第 1 槽该字段只是空数组，算出来的键也会变化。[上下文与摘要函数](../../../../backend/app/services/preparations.py#L423) · [Worker 命中条件](../../../../backend/app/workers/runner.py#L590)

复查用本地开发库里实际保存的 `generated-1` 和 `generated-2` 做过只读对照。两条记录都匹配去掉这一字段的历史摘要，都不匹配含这一字段的当前摘要。这样一来，原本只需补第 3 道题的旧任务，升级后会重新向模型请求前两道。现有缓存复用测试的首次生成和重试都使用同一份新版代码，覆盖不到该场景。[当前复用回归](../../../../backend/tests/test_jobs.py#L742)

## 二、推荐实现

### 1. 保持新写入格式，读取时精确兼容旧键

在 `JobWorker._handle_plan` 使用现有 `generation_context_hash(context)` 计算当前键。缓存存在且当前键未匹配时，复制本槽上下文，**只移除 `previous_summaries`**，用同一函数计算历史键。比较时允许其中一个精确匹配。新生成的题仍通过现有 `_save_slot` 写入当前键。

等价的逻辑示例如下。可内联到现有缓存判定，按需避免为没有缓存的槽位额外计算摘要。

```python
context_hash = generation_context_hash(context)
saved_hash = cached.get("context_hash") if isinstance(cached, dict) else None
hash_matches = saved_hash == context_hash

if isinstance(saved_hash, str) and not hash_matches and "previous_summaries" in context:
    legacy_context = dict(context)
    del legacy_context["previous_summaries"]
    hash_matches = saved_hash == generation_context_hash(legacy_context)
```

继续校验缓存数据的结构、当前 `WORK_ITEM_VALIDATION_VERSION` 和题目对象类型。复用范围仍限定为当前任务 ID 的已验证工作项，不允许跨任务、跨准备复制。历史键也覆盖材料快照、匹配报告、准备版本、题量、量表、依据卡和已有禁止题干等输入。保留这些字段参与计算。若将来 `previous_summaries` 成为业务校验的输入，需要随校验规则重新评估兼容口径。

### 2. 命中任何一个键后都重新校验

1. 保留当前 `_validate_generated` 调用，包括本槽题型、量表、允许的已审依据卡、材料归属和锚点、题库及前序题去重。只有重新校验通过，才把题加入 `generated`。
2. 沿用同一条摘要生成路径。历史缓存命中时，也要给后续槽位加入该题的考察摘要和禁止题干。生成第 3 槽时，模型应仍然看到已通过的第 1、2 槽。
3. 任一缓存无法匹配或重新校验失败，就用正常路径生成该槽位。后续槽位按真正选中的前序题重新计算输入。继续通过 `save_work_item` 的目标版本和任务租约检查写入。
4. 历史缓存可以直接读取使用，无需数据库迁移或批量回写。终态规则、显式重试资格、模型调用预算、最终语义复核和统一发布流程沿用原实现。[重新校验与槽位写入](../../../../backend/app/workers/runner.py#L596) · [任务租约与槽位持久化](../../../../backend/app/services/jobs.py#L463)

## 三、跨版本回归

用隔离 PostgreSQL 和模拟 provider，在 [已有复用回归](../../../../backend/tests/test_jobs.py#L742) 旁增加针对性用例。最重要的断言是**恢复后出题调用列表只含 `generated-3`**。

1. 用合成简历和 JD 创建六题准备，完成匹配。第一次生成让第 1、2 槽成功、第 3 槽模拟 `AI_TIMEOUT`，将任务停在仍可合法重试的第 1 次失败。
2. 让测试中的前两条 `JobWorkItem` 模拟旧 Worker 写入。可以在首次生成时，用独立的测试辅助逻辑对去掉 `previous_summaries` 的副本调用既有 canonical 哈希。也可以在隔离测试库设置两条旧格式夹具。升级后运行二次任务时，启用实际生产读取逻辑。历史摘要的构造独立于待测的兼容判定，避免两边同一个错误导致测试误过。
3. 开始重试之前，明确断言两条记录与旧格式相等、与当前格式不同。重新构建的当前上下文中，第 1 槽的 `previous_summaries` 为空列表，第 2 槽有第 1 槽的考察摘要。保留原任务 ID，从现有重试 API 提交 `expected_attempt=1`。检查只跑第三槽的出题调用，且请求仍带第 1、2 槽的摘要和禁止题干。最终语义复核是独立的一次调用，继续照常执行。
4. 核对最终只发布一份完整计划，三道题库题加三道 AI 题。原先两道合格 AI 题的内容保持一致。

| 补充用例 | 预期 |
|---|---|
| 当前版本写入的摘要 | 现有同版本复用回归继续通过。 |
| 历史键业务输入不同 | 前序题干、材料快照、依据或验证版本任何一项不符，都跳过不适用的缓存。可直接在测试夹具中构造旧摘要差异。 |
| 旧键正确，缓存题未通过当前校验 | 模拟缓存题和本次禁止题干冲突，确认重新生成该槽位，且错误题不进入计划。 |
| 原任务已用完两次尝试 | 资格保持为不可重试。截图中的任务继续走「沿用材料新建准备」，新准备不继承旧槽位。 |

## 四、执行与交付

在已配置隔离 PostgreSQL 测试库的终端，从仓库根目录进入 `backend`。pytest 会重建目标测试 schema。[测试库设置](../../../overview/本地开发.md)

```powershell
& ../.work/venv/Scripts/python.exe -m pytest tests/test_jobs.py tests/test_generation_slots.py tests/test_plan_flow.py -q
& ../.work/venv/Scripts/python.exe -m pytest tests -q
```

交付汇报兼容代码位置、跨版本实际调用过的槽位、本轮测试结果。上一轮复查基线为后端 227 项、Android JVM 113 项通过。本轮缓存修复在后端完成，只需在涉及 Android 的情况下重新验证相关客户端行为。开发环境采用当前代码启动 Worker 后，符合资格的旧任务才会用到新逻辑。已耗尽次数的真实任务保留原状态，跨版本恢复用隔离测试记录验证。

## 可复制给执行模型

> 按《MockMate 计划槽位缓存跨版本兼容修复指南》修复上一轮 P2。Worker 读取时同时兼容当前键和只少了 previous_summaries 的历史键，命中后继续执行现有题目校验。让已通过的题进入后续摘要，补旧版保存前两槽、新版只向模型请求第 3 槽的回归。保留任务次数、发布规则和现有未提交改动，回报实际测试结果。
