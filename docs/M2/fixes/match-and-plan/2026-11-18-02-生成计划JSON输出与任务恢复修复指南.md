# MockMate 生成计划 JSON 输出与任务恢复修复指南

修复模型出题返回无法解析的 JSON、计划任务失败后没有可用重试，以及页面重复显示同一错误的问题。实施前用 `git status --short` 核对当前代码。上一轮匹配证据修复已有未提交改动，应一并保留。两次故障各有自己的验证入口。[匹配分析修复指南](2026-11-18-01-匹配分析证据引用修复指南.md)

## 一、这次失败发生在哪里

我按截图任务 ID 只读查询了本地开发库。当前准备版本为 4，有已生成的匹配报告，选择的是六道主问题。该计划任务是第 1 次尝试，在 `generated-1` 连续两次返回 `AI_INVALID_OUTPUT`，最终原因是「AI 返回内容不是合法 JSON」。两个调用均使用 `deepseek-flash`，没有已通过校验的出题槽位，也没有发布计划。后续 AI 题和全局语义复核均未运行。

这个错误由 `json.loads(choices[0].message.content)` 抛出，发生在题目字段、量表、引文和去重校验之前。适配器已发送 `response_format=json_object`，没有显式配置生成长度，也没有保存 `finish_reason`。两次 completion token 为 3,741 和 2,416，其中 reasoning token 为 2,647 和 969。现有记录无法判断是截断还是其他 JSON 格式问题。这次报错无需先修改简历、JD 或题量。[DeepSeek 适配器](../../../../backend/app/ai/provider.py#L744) · [槽位执行与纠正](../../../../backend/app/workers/runner.py#L1068)

两张失败卡来自同一任务。计划页同时显示 `JobRecoveryActions` 和 `state.planError`，后台任务失败时也会填充 `planError`。当前 `plan` 对这类错误不可显式重试，同版本再次点「生成计划」会复用原任务。[计划页面](../../../../android/app/src/main/java/com/mockmate/app/ui/screens/PlanScreens.kt#L365) · [任务失败归并](../../../../android/app/src/main/java/com/mockmate/app/ui/AppViewModel.kt#L2971) · [任务复用](../../../../backend/app/services/jobs.py#L133)

## 二、区分输出故障并缩小生成请求

### 2.1 诊断与错误映射

1. 在 `DeepSeekProvider._chat_json` 取得请求 ID 和 usage 后，从第一条 choice 提取 `finish_reason`。同步更新 Worker 的 `_append_ai_record`，把结束原因和现有的阶段、槽位、请求 ID、token 用量记录在 `ai_call_records`。旧调用记录和测试响应没有该字段时显示未知。记录元数据即可，避免新增响应正文、思考文本、密钥、原材料和完整提示词日志。[适配器解析](../../../../backend/app/ai/provider.py#L800) · [Worker 调用记录](../../../../backend/app/workers/runner.py#L175)
2. 沿用公共错误码 `AI_INVALID_OUTPUT`。给计划出题的失败写入字符串详情，例如 `stage=plan`、`slot=generated-1`、`reason=output_truncated`、`finish_reason=length`。其他格式原因可用 `empty_content`、`invalid_json` 或 `invalid_question_schema`。adapter 确定具体原因，Worker 补阶段和槽位。检查 `_generate_slot` 的最终异常包装，确保结构化原因不会被截断或只剩通用文案。
3. `finish_reason=length` 优先判为输出未完整结束，即使返回的部分碰巧能被 JSON 解析。对 `stop` 或缺省原因，分别识别空白 content、非法 JSON、非对象 JSON 和题目字段错误。现有 HTTP 错误、认证失败、超时和限流按原规则返回。上游明确标记内容过滤时，不当作格式错误自动纠正。DeepSeek 官方文档说明 JSON 模式可能出现空白内容，`length` 也可能伴随文本截断。[Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/) · [DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)

### 2.2 计划出题的调用和提示词

1. 保留 `response_format={ "type": "json_object" }`、严格的 `json.loads` 和 `GeneratedQuestionOutput`。在 adapter 增加由计划出题入口显式传入的请求选项。用 `deepseek-flash` 做合成六题对照时，先试 `thinking={ "type": "disabled" }` 和 `max_tokens=4096`，按实测的结束原因、token 用量和题目质量调整。这个数值是测试起点。保留配置回退，兼容端点只发送其支持的参数。材料解析、匹配、计划语义复核、追问和评分延用各自请求设置。[生成题适配入口](../../../../backend/app/ai/provider.py#L953) · [DeepSeek 思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)
2. 精简 `generate_prompt` 中重复的题干黑名单、材料结构、锚点和量表。保留岗位／级别、槽位类型、匹配重点、允许锚点完整值、可用依据卡、量表和参与去重的题干。完整原文可作语境，优先移除重复的结构序列化。裁剪前核对不会截断允许引用的证据，也不会使模型丢失区分经历题和知识题所需的信息。[生成提示词](../../../../backend/app/ai/prompts.py#L179) · [上下文构造](../../../../backend/app/services/preparations.py#L367)
3. 修正自相矛盾的 JSON 示例。目前正文要求 `uncertainties=[]`，示例给了非空文本。示例的 anchor 和 material ref 从同一个真实候选取得。knowledge 示例使用本槽允许的已审依据卡，experience 示例使用材料依据。要求输出单个 JSON 对象且恰好一题。继续执行现有量表、题干去重、逐字引文、依据、可信度和来源配额校验。
4. 保留「初次生成 + 最多一次纠正」的槽位预算。对于明确截断，在已有纠正机会里要求缩短可选解释，必要时按配置提高上限；对于空白或非法 JSON，要求重新产出同一个槽位的完整 JSON。纠正请求带失败原因，不带非法原文。两次都失败时保留最后一次结构化原因。服务端仍严格解析完整 JSON，不补括号或从任意文本提取片段来发布计划。

## 三、让原失败任务可恢复

1. 为 `kind=plan` 的明确格式失败开放显式重试。建议允许 `output_truncated`、`empty_content` 和 `invalid_json`，以 `stage=plan` 和有效生成槽位约束范围。兼容截图里的旧格式，要求错误码为 `AI_INVALID_OUTPUT`、消息为「生成槽位在有限纠正后仍不合法」，且详情由有效生成槽位编号和「AI 返回内容不是合法 JSON」组成。其余业务校验失败继续按原规则处理。保留网络错误以及上一轮 `match`、追问和报告的重试资格。
2. 通过 `is_retryable` 动态计算资格。复用 `POST /v1/jobs/{job_id}/retry`、`expected_attempt`、幂等键、任务归属、输入版本以及默认两次任务尝试上限。新版 API 和 Worker 同时启动后，原第 1 次失败且输入仍当前的任务查状态即可得到可重试资格。只在用户明确点击重试时增加 attempt、用原任务 ID 排队。打开页面、查询、重复点击「生成计划」或服务重启继续按原读取或复用逻辑运行。[重试资格](../../../../backend/app/services/jobs.py#L232) · [重试路由](../../../../backend/app/api/jobs_routes.py#L44)
3. 保留 `JobWorkItem` 槽位复用。只复用同一任务、上下文摘要和验证版本符合、且重新校验通过的槽位。未通过的槽位重新生成。业务校验口径有变化时评估缓存版本，纯请求设定变化可继续使用仍符合当前校验的题。全部槽位通过后再进行语义复核及最终发布，沿用准备版本与任务租约检查。六题始终为三道题库题加三道 AI 题。[槽位复用](../../../../backend/app/workers/runner.py#L475)

## 四、计划页只显示一个当前任务的失败入口

1. 根据 `state.job` 的任务种类、准备 ID 和输入 revision 判断归属。当前计划任务的失败由一张任务卡展示可展开诊断、只读查询和有资格的重试。若 `planError` 来自同一个后台任务，合并或跳过重复卡。尚未入队的同步错误，例如 `BANK_INSUFFICIENT`，继续专门展示匹配到的题库数量和可执行入口。
2. 在 `ErrorDiagnosticsMapper` 优先识别结构化详情，兼容已有两个位置字段。这个案例可显示「AI 生成的第 1 道题返回了无法读取的结果。本次计划未保存，已确认的材料和匹配报告已保留。」只有明确出现 `length` 才显示「模型输出中途结束」。有资格显示「重试生成计划」，沿用现有重试与轮询。无资格时按次数用尽或输入已更新等实际状态说明。[错误映射](../../../../android/app/src/main/java/com/mockmate/app/ui/ErrorDiagnostics.kt#L80) · [现有重试逻辑](../../../../android/app/src/main/java/com/mockmate/app/ui/AppViewModel.kt#L1643)
3. 当前版本已有排队、运行或失败任务时，让主要操作对应任务状态。用户从真正的重试入口发起请求。准备版本更新后，允许正常开始新计划。异步回包按当前账号、页面、准备和版本归并，继续支持原有只读刷新和后台恢复。

## 五、实施验收

| 验证场景 | 通过标准 |
|---|---|
| 第一次返回 `finish_reason=length` | 识别为输出未完成，记录结束原因和槽位。现有一次纠正返回有效 JSON 后通过。 |
| 空白、非法 JSON、字段类型不符 | 分类清楚。旧模拟响应省略 `finish_reason` 仍可用。两次都不合法时，调用数为二，任务失败，计划未发布。 |
| 请求选项范围 | 用模拟 HTTP 捕获出题、纠正和计划语义复核的请求。非思考配置与输出预算只进入出题路径。 |
| 旧计划任务与重试次数 | 预置截图形状的旧失败记录。GET 返回可重试，手动点击后原任务 ID 的 attempt 加一。只读、过期版本、次数已用尽、其他账号和非格式业务错误都按现有规则处理。 |
| 已通过校验的槽位 | 重试时复用符合上下文与验证版本的槽位，只生成失败或缺失槽位。合成六题经过证据、去重、量表、三加三配额和计划确认。 |
| Android 计划页 | 后台失败只显示一张卡，状态允许时可实际点击重试。同步题库不足仍显示数量及返回设置入口。旧准备或旧版本的结果不能覆盖当前页面。 |

## 可复制给执行模型

> 按《MockMate 生成计划 JSON 输出与任务恢复修复指南》实施。先记录 DeepSeek 的结束原因和结构化格式故障，收窄并验证计划出题设置，修正提示词与一次纠正。让当前输入版本的格式失败任务沿用已有的显式重试，并保留已通过校验的槽位。合并计划页重复失败卡，保留题库不足提示。保留未提交的匹配修复和三加三配额，执行回归并汇报实际结果。
