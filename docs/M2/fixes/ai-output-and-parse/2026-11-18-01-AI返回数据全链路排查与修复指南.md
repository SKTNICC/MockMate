## 2. 统一模型响应的处理顺序

在现有 Provider、业务校验和 Worker 流程中按以下顺序落实。DeepSeek 和本地测试 Provider 的输出都要经过保护业务结果的校验。

1. **检查 HTTP 响应与结束原因。** 在 `_chat_json` 保留现有超时、网络、鉴权、限流和内容过滤分类。先验证响应信封、首个 choice 和 message。在 DeepSeek 路径处理明确的 `length`、`aborted`、`insufficient_system_resource` 和 `tool_calls`，即使正文能解析也停止使用该响应。只有预期的完成原因可进入正文校验。对于已有兼容代理或 Mock 省略结束原因的情况，先补测试确认实际调用方，再按需要显式兼容缺省，记录 `unknown`。明确返回未知值也要有单独失败分支。空内容单独归因。DeepSeek JSON 输出选项继续使用，应用仍负责验证返回值。[DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)
2. **严格解析正文。** 正文须为单个 JSON 对象。用 `object_pairs_hook` 拒绝任意层级的重复键，用 `parse_constant` 拒绝 `NaN` 和 `Infinity`，并用有限数检查拒绝 `1e999` 等溢出值。把非法 JSON、非对象、空正文和信封非法映射到各自可测的原因。对嵌套过深等解析异常给出可控错误。代码围栏、附言、截断和拼接对象交由该阶段按有限恢复策略修正，不从混杂文本里截取一个对象直接发布。
3. **用每个阶段的输入模型约束 AI 增量。** 复用现有 Pydantic 模型和业务校验。需加强类型时，优先定义仅服务端模型入口使用的字段或模型，再映射到现有业务结构。给语义关键字段使用显式必填和相应严格类型，例如严格布尔值和整数。JSON 中合法的 UUID 字符串仍应可解析。保留 `extra="forbid"`。提示词展示的结构示例用对应入口模型跑测试，业务结果接着用真实校验器验证，避免提示词、Provider、Worker 三处各维护一份互相漂移的规则。
4. **把外部数据绑定到服务端当前事实。** 材料事实来自该版原文或已确认快照。问题、回答、维度、技能码从本次已知集合检查。引用要求非空白，比较时使用原字符串做连续子串检查。可由服务端确定的引用、维度名称和权重沿用原有权威来源。补正只处理业务允许为空的标签或确定的外壳差异。缺少必要事实、歧义字段、未知引用和语义矛盾按该阶段失败处理。
5. **入库和恢复时走相同校验。** 新结果和复用缓存都校验，发布前继续检查当前版本、锁与 Worker lease。只提交完整结果。阶段可按现有规则显式重试时，复用同一 Job、幂等键和 `expected_attempt`；读状态只读。保留已有槽位续跑、计划 3+3 和面试答题进度。

### 失败分类和请求预算

在现有 `ErrorInfo.details: list[str]` 内新增稳定的 `stage=`、`reason=`、`slot=`、`field=` 项。字段路径来自已知 schema 和数组下标，未知键归为 `extra_field`。可用 `source=provider_output` 区分模型产物错误与输入或设置错误。先在适配器侧把 `ValidationError` 转成受控错误，只预期捕获结构、解码和类型异常。业务证据与状态错误继续使用原有错误码，带上安全的阶段与原因。向 App 保留旧错误码和回退文案。把信封非法、字段非法、证据非法、模型中断和发布前版本变化分别记录，字段摘要使用白名单并限长。

解析首次先允许一次有明确校验反馈的纠正，可复用现有调用封装。合法但证据没对上的结果是否纠正，由现有解析业务校验的错误类型决定。对截图这类结构错误，若纠正仍失败，由用户选择重试同一任务或手动核对。计划生成沿用每槽一次初始生成加一次纠正，避免再叠一层通用补调。计划复核、评分、追问沿用显式任务恢复，保持用户可用的继续操作。复核明确发现重复或无依据、内容被拦截、设置错误、输入过期时，走各自现有业务恢复，避免用重复模型调用绕过这些结果。

计划出题的 `AI_PLAN_GENERATE_*` 仅作用于原来的阶段。`_chat_json` 对不支持 `thinking` 的兼容请求，应匹配明确的供应商拒绝信号并保留最多一次的回退。把回退这种实际 HTTP 请求计入预算，记录是否发生，避免同一个结构纠正循环反复触发兼容回退。[调用入口](../../../../backend/app/workers/runner.py#L236) · [DeepSeek 请求与回退](../../../../backend/app/ai/provider.py#L747)

## 3. 先修复上传简历后的解析

### 3.1 让提示词与材料结构一致

在 `parse_prompt` 分别展示简历工作经历和项目的真实形状。JD 同样分别展示职责和要求。把完整示例与“没有该类材料时用空数组”的说明放在一起。样例引文逐字来自合成原文，使示例可以在测试里同时通过结构和证据校验。以下为简历响应示例，示例原文包含两处引文。

```json
{
  "kind": "resume",
  "education": [],
  "work_experience": [
    {
      "item_id": "work-1",
      "organization": "示例实验室",
      "title": "开发实习生",
      "description": "维护库存接口",
      "evidence": {"quote": "示例实验室｜开发实习生｜维护库存接口", "origin": "extracted"}
    }
  ],
  "projects": [
    {
      "item_id": "project-1",
      "name": "库存工具",
      "description": "用 Java 编写库存查询",
      "skill_codes": [],
      "evidence": {"quote": "库存工具｜用 Java 编写库存查询", "origin": "extracted"}
    }
  ],
  "skills": []
}
```

工作经历的 `organization` 和 `title` 按原文提取。没有工作经历的简历可返回 `work_experience: []`。原文明示有经历但组织或职务无法定位时，按缺失必要事实处理，纠正后仍缺失就引导用户核对原文。工作经历里的 `name` 语义不明确，禁止自动改名为组织或职务，禁止把缺失职务补成固定头衔，禁止直接删除一段原文中确实存在的经历来让整个对象通过。加入组织或职务系编造的用例，给该阶段定义可执行的原文关联规则，同时兼容原文中的合法标点与空格。[简历与 JD 结构](../../../../backend/app/schemas.py#L54) · [材料校验](../../../../backend/app/services/text.py#L110)

JD 的结构校验目前允许任意非空 `role_id`，目录校验留到确认阶段。把目录中不存在的岗位或无效岗位／级别组合提前归为模型数据错误，解析保存前复用 `ensure_jd_profile_compatible`。若原文确有冲突或解析出另一个目录内有效组合，保留事实并走现有用户调整流程，匹配入口仍要求 JD 与本次准备设置一致。测试时区分模型编造的岗位码与原文中的真实岗位冲突。[目录校验](../../../../backend/app/services/catalog.py#L105) · [确认材料](../../../../backend/app/services/materials.py#L286) · [匹配创建](../../../../backend/app/services/preparations.py#L238)

### 3.2 把纠正限制在可验证的数据

在 `parse_material`、`_handle_parse` 之间选一个位置统一管理解析纠正次数。初次结构错误时，纠正请求只给该次任务原文、安全字段路径、错误类型和正确结构示例，可沿用同一次用户授权上下文。最终响应重新走完整结构、技能词表和证据校验。仅在最后一次写入事务内重读 Job 和材料版本，且材料尚未产生结构结果时写入。已有手工编辑或版本更新时按当前流程结束或提示状态已变化。

沿用现有技能码清理。技能名称可信但无匹配编码时保留名称并置 `code=null`，项目和 JD 要求的可选标签按当前词表过滤。空白引用、无原文支持的引用、重复条目 ID、错位字段和缺失职务都要进入各自的校验。模型解析结果只能使用 `origin=extracted`，用户填写继续沿用人工确认流程。[解析 Worker](../../../../backend/app/workers/runner.py#L367) · [技能标签修复记录](../skill-catalog/2026-11-18-01-技能标签与AI解析修复指南.md)

### 3.3 让失败的原任务可以恢复

- 在 `jobs.is_retryable` 增加解析阶段的结构、正文和限定的模型证据输出错误。优先使用稳定的 `stage=parse` 和 `reason=`。为已经落库的截图这类失败保留窄兼容，限定 `kind=parse`、`AI_INVALID_OUTPUT`、现有结构错误消息及已知解析字段错误形状。由同一个函数生成 GET 上的 `retryable` 并检查 POST 重试条件。
- 解析重试要求当前用户、材料及 revision 一致，存在可用原文，且该版还没有结构结果或已确认快照。注意 ORM 读到的 JSON `null` 和 SQL `NULL` 可能是不同的数据库表示，要按业务字段是否有结构结果判断。重试仍通过 `POST /v1/jobs/{id}/retry` 和当前 `expected_attempt`，遵守配置中的总尝试上限。测试同一版本的并发点击、旧 attempt、手工确认后重试及输入过期。保留现有 Job ID 和失败记录，无需手工改数据库或修改简历来制造新版本。
- Android 在核对页以当前材料和 revision 对应的 Job 显示恢复操作。可重试时显示“重试 AI 解析”，已耗尽时提供当前已有的手动填写入口。正文可用时可显示“原文已保留，可以手动核对”。启动按钮按当前阶段和 Job 状态显示，同一失败任务复用重试入口。状态查询保持只读。
- 失败时显示一个持续可见的状态区，Toast 只给短提示；状态区里的详情默认折叠。诊断复制只含安全字段路径、原因、任务标识与尝试次数，针对旧任务复制时同样过滤模型文本片段、材料内容和用户回答。普通文案无需提示用户先更换岗位或修改已有材料来绕过结构错误。[解析任务创建](../../../../backend/app/services/materials.py#L250) · [Job 重试](../../../../backend/app/services/jobs.py#L309) · [Android 核对页](../../../../android/app/src/main/java/com/mockmate/app/ui/screens/MaterialScreens.kt#L435) · [错误诊断](../../../../android/app/src/main/java/com/mockmate/app/ui/ErrorDiagnostics.kt#L46)

## 4. 修复其余阶段并复用验证方式

### 4.1 匹配与生成题

- 匹配保持“模型返回 requirement 和材料条目 ID，服务端还原证据”的方式。断言要求恰好覆盖一次，白名单之外、跨快照或重复引用会失败。支持状态须有可验证证据，`not_evidenced` 无支持证据。把旧错引文加入回归，确保返回给 App 的引文只来自指定条目。不要重新用模型的自由文本组装结构化引用。[匹配证据修复记录](../match-and-plan/2026-11-18-01-匹配分析证据引用修复指南.md)
- 生成题用本槽上下文和当前词表验证标签。若标签确实为可选元数据，将词表外值过滤后再写槽位，否则判为槽位无效。用同一个规则处理新响应和缓存恢复，并保留计划发布门槛。验证给模型的 `allowed_anchors` 与实际可接受引文一致。至少检查属于本次允许的材料条目、来自对应快照且逐字可定位；若要求引用完整锚点，提示词与验证同时要求匹配同一条允许锚点。题干、权重、指定题型和评分标准继续走现有校验。
- 保留生成槽位的哈希、旧版哈希兼容和畸形缓存回退。重试时只重新生成失效槽，题库仍为 3 题，AI 仍为 3 题。保留此前的题干去重措施和真实重复诊断。将兼容与修复路径放入已有槽位回归。[计划重复题修复](../match-and-plan/2026-11-18-03-生成计划重复题修复与续跑指南.md) · [旧版缓存兼容](../match-and-plan/2026-11-18-04-计划槽位缓存跨版本兼容修复指南.md) · [畸形缓存回退](../match-and-plan/2026-11-18-05-计划槽位畸形缓存回退修复指南.md)

### 4.2 计划语义复核

给模型结果使用必填 `duplicate_pairs`、`grounding_issues`、严格布尔 `uncertain`。没有发现时，两组数组由模型显式返回 `[]`，在现有 `review_prompt` 中写明这条规则。复用提示词已有的字段形状，数组元素使用具名 Pydantic 模型，重复项包含 `left_id`、`right_id`、`reason`，无依据项包含 `question_id`、`claim`、`reason`。文本必须非空白，ID 必须属于本次题集，拒绝自配对、正反向重复、重复问题记录。类型校验要早于集合查询，以免数组型 ID 触发 `TypeError`。

把私有模型校验后的数据映射到已有的计划复核存储结构，兼容读取已发布计划。缺字段和畸形响应归入 `stage=plan_review`，可针对格式错误增加一次显式任务重试并复用已生成槽。真正的重复、无依据和 `uncertain=true` 继续走现有发布阻断。禁止用 `[]` 或 `false` 补齐缺失字段以获得复核通过。[复核提示词](../../../../backend/app/ai/prompts.py#L450) · [复核 Worker](../../../../backend/app/workers/runner.py#L1291)

### 4.3 追问

按 `ask` 和 `advance` 两个分支校验。发起追问时，题干、目标和引文全部需有非空白内容，引用当前回答，按原字符做连续子串校验并遵守长度限制。继续主问题时按提示词约定返回空值，兼容已明确支持的缺省形式，不携带追问内容。用失败任务状态承接非法结果，保留主回答，按现有条件允许重试或跳过，并保持一次主问题最多一次动态追问。[追问提示词](../../../../backend/app/ai/prompts.py#L495) · [追问校验](../../../../backend/app/workers/runner.py#L841)

### 4.4 评分与报告缓存

- 对评分入口的 `score` 单独启用严格整数，接受 JSON 数字 `0` 至 `4` 的整数表示，拒绝布尔、字符串和浮点。复用 `validate_question_score` 对当前题目、维度完整性、同题回答与逐字引文的校验。将纯空白引文加入既有无效证据分支。命中该分支继续降为 `uncertain`，清空分数、证据和该维度建议。非计分状态保持无分值和无引文，合法的零分仍计入报告。
- 给报告槽位增加明确的已规范化结构校验，至少检查 `question_id`、行与载荷的 `content_hash`、`dimensions` 及其元素的类型和字段。让 Worker 跳过已有槽前与报告发布共用同一个读取及验证函数，使用当前题目、回合、回答重验维度和证据。没有兼容读取需求的畸形载荷按坏槽处理；有历史有效写入形式时，先加合成兼容用例再映射。读到坏槽时只补做该题，完成后在原有锁及 lease 检查下保存。仅捕获确定的缓存内容校验错误，数据库异常和 Worker 故障走原本处理。
- 发布检查保留题目覆盖、哈希和一致性门槛。校验失败时报告不可显示为已生成。若任务最终失败，按当前业务条件提供重试或基础报告，已结束的面试和回答历史仍可使用。[单题评分校验](../../../../backend/app/services/interviews.py#L1246) · [报告 Worker](../../../../backend/app/workers/runner.py#L994) · [报告发布](../../../../backend/app/services/interviews.py#L1575)

## 5. 日志与诊断的验收

`_call_ai` 当前记录 Provider 调用结果，出题槽另外有业务校验注记。沿用这个记录入口，给各阶段补同样的关联信息，区分请求返回、结构校验、业务校验和最终发布。建议每条记录有 Job、任务 attempt、stage、slot、是否纠正或参数回退、白名单内的 finish reason、错误分类和字段路径。默认只存摘要。检查既有证据错误的 details 是否夹带引用片段，并在向 UI 及剪贴板投影时只保留安全字段。可用合成测试植入标记，断言 API 错误体、Job 日志与诊断复制都不出现标记原文。[现有调用记录](../../../../backend/app/workers/runner.py#L192) · [Android 诊断模型](../../../../android/app/src/main/java/com/mockmate/app/ui/ErrorDiagnostics.kt#L46)
