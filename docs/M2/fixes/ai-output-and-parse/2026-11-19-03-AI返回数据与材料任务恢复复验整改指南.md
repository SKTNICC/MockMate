# MockMate AI 返回数据与材料任务恢复复验整改指南

复验当前工作区后，还有五组问题。后端在独立 PostgreSQL 测试库通过 248 项测试，Android 通过 118 项 JVM 单元测试，Debug APK 构建、契约生成和地基校验通过。原真机解析任务只读查询仍返回 `retryable=true`，组织和职务缺失两条诊断仍可读。本次用合成材料和模拟 HTTP 验证异常，未重试真实历史任务、未调用外部模型或进行真机复验。

保留此前对 JSON 重键、非有限数字、空字符、孤立 surrogate、明确中断、显式未知结束原因的拦截。继续复用现有 Job、版本、尝试次数、幂等与槽位续跑，保持公开契约和计划 3+3。以下为本轮需要补齐的路径。

## 1. 退出后立即重开同一材料，任务状态可能一直加载（P1）

**已用 Android JVM 专项探针复现。** 第一次打开材料 A，`GET /v1/jobs/{id}` 尚未返回时退出，立即重开 A。新页面先把查询状态设为 `LOADING`。读请求的去重键只包含材料 ID、版本和 Job ID，第二次请求与第一次相撞后直接返回。旧请求回来时页面代数已变化，结果被丢弃。探针确认只发出了首次 Job GET，旧请求返回后新页面仍处于 `LOADING`，开始按钮和只读查询按钮都未出现。上一轮的切换测试使用了不同的材料 ID，未触发此路径。[打开核对页和置为加载](../../../../android/app/src/main/java/com/mockmate/app/ui/AppViewModel.kt#L992) · [查询去重和 scope 检查](../../../../android/app/src/main/java/com/mockmate/app/ui/AppViewModel.kt#L1071) · [按钮策略](../../../../android/app/src/main/java/com/mockmate/app/ui/screens/MaterialScreens.kt#L375) · [已有切换材料测试](../../../../android/app/src/test/java/com/mockmate/app/ParseRecoveryAndDiagnosticsTest.kt#L506)

另一个恢复缺口可从代码路径确认。Job GET 成功后，当前实现先标为 `LOADED`，再判断是否需要取回材料结果。若这时 `GET /materials/{id}` 或快照 GET 失败，通用错误效果只提示错误，页面仍持有旧材料且没有对应的只读恢复入口。这个时序在提取成功但页面还无正文、解析成功但页面还无 profile 时都会出现。[读取 Job 后提前标记完成](../../../../android/app/src/main/java/com/mockmate/app/ui/AppViewModel.kt#L1107) · [回读材料和快照](../../../../android/app/src/main/java/com/mockmate/app/data/RestoreJobService.kt#L377)

1. **让读取去重与页面生命周期一致。** 只读查询可按账号、会话代数、页面代数、材料、revision 和 Job ID 去重，或让新的页面订阅同一在途请求并以自己的 scope 处理。保持同一页面点两次只发一次 GET，旧页面的请求不能导致新页面无请求可等。保留写操作自己的幂等防重复，读取恢复无需触发 POST。
2. **等资料真正到达再结束恢复状态。** 对于已完成的提取和解析且当前页面还缺结果，保持加载直至资料投影返回；读资料失败可切到 `FAILED` 并提供同一条只读查询入口。修正错误分支时继续检查当前账号、页面代数、材料 ID、版本及任务尝试次序，晚到的响应不能倒退状态。状态查询和手工核对都沿用当前页面职责。
3. 在现有 `ParseRecoveryAndDiagnosticsTest` 用 `CompletableDeferred` 控制第一次 Job GET。进入 A 后先退出并重开同一 A，再放行旧 GET。断言新页面最终显示可重试状态或进入可恢复查询失败状态，当前 Job 仍为 A，未发解析 POST。再覆盖已完成的提取或解析第一次回读 HTTP 503，下一次只读恢复取得正文或 profile。旧请求迟到与连续点击分别单独验证。

## 2. 连续字段标签的工作经历仍可跨条目拼接（P1）

**已用当前解析结构模型和业务校验复现。** 合成原文如下。

```text
公司：示例甲实验室
职位：后端实习生
职责：维护库存接口
公司：示例乙银行
职位：数据实习生
职责：开发台账工具
```

构造一条工作经历，组织为“示例甲实验室”，职务为“数据实习生”，引用覆盖全部六行。当前代码会检查两者都出现在引用中，再根据空行、同一行的分隔符、条目编号、日期行或其它已返回引文识别跨段。示例没有这些信号，且模型只返回一条，所以结果通过。它会形成待核对的错误草稿，用户确认后可成为匹配或出题上下文。[跨段判断](../../../../backend/app/services/text.py#L179) · [组织和职务校验](../../../../backend/app/services/text.py#L352)

1. 优先识别**服务端原文里的经历段落**，再检查模型引用是否有一处从头到尾落在同一段。将重复出现的“公司／单位／组织／雇主”和其后的“职位／岗位／职务”视为明确边界，并保留空行、编号、日期等已有可复用信号。不要依赖这次模型同时返回两段，原文应足以识别本例。
2. 保留引用与原文逐字一致和组织／职务对照。对能明确分段的布局，只接受支持该段组织与职务的连续引文。处理同一公司的两次任职时，仍应区分职务各自所处的段。对证据无法确定的布局走现有有限纠正和人工核对。避免把同一条经历内的多行职责、编号列表或日期说明误判成多段经历。
3. 加入上述无空行反例、英文 `Company/Title` 对照、同公司两段任职、公司与职务分属相邻行的合法输入、单段包含多条编号职责，以及确实没有工作经历的输入。至少加一个 Worker 端到端用例，先返回跨段引文再返回同条引文，断言只有通过校验的草稿入库。

## 3. DeepSeek 的 400 参数回退仍可能误触发或抛异常（P2）

**用 HTTP MockTransport 复现三种响应。** `loc` 为数字会导致适配器尝试迭代整数，抛出 `TypeError`，之后 Worker 会归为 `INTERNAL_ERROR`。其余两种都额外发送了一次请求，并错误地把 Provider 实例记为不支持 `thinking`。[400 判定函数](../../../../backend/app/ai/provider.py#L121) · [请求回退](../../../../backend/app/ai/provider.py#L1038)

| 合成 400 响应 | 当前实际结果 | 预期 |
| --- | --- | --- |
| `{"detail":[{"loc":123,"type":"extra_forbidden"}]}` | 1 次 HTTP，裸 `TypeError` | 1 次 HTTP，`AI_REQUEST_REJECTED` |
| `{"error":{"code":"invalid_parameter","message":"max_tokens exceeds limit. thinking is enabled."}}` | 2 次 HTTP，记为不支持 `thinking` | 1 次 HTTP，保持配置 |
| `{"detail":[{"loc":["body","thinking","type"],"type":"value_error","msg":"Invalid thinking mode value"}]}` | 2 次 HTTP，记为不支持 `thinking` | 1 次 HTTP，保留参数值错误 |

1. 对 400 解析先验证对象、数组和元素字段类型。`loc` 仅接受来源实际使用的路径数组，支持字符串字段和整数下标。类型畸形或 JSON 解码异常时，直接沿用原 HTTP 的受控错误，避免响应说明影响错误归类。
2. 只在证据明确表明顶层 `thinking` 参数不存在或不受支持时允许一次回退。顶层字段多余和该字段的子值非法有不同含义。无参数名的通用 `invalid_parameter` 和消息中另处提到 `thinking` 时需要明确关联才允许回退。先识别内容过滤等明确拒绝信号。
3. 保留已有明确不支持的正例，验证一次回退和 HTTP 次数记录。给表中的三例逐项断言调用数、业务错误码和后续请求是否保留配置。追加深嵌套错误信封或无效 JSON 样例，验证 400 辅助判定在畸形输入下也不抛裸异常。

## 4. 空简历结果和重复条目未进入已有恢复路径（P2）

**已复现。** 模型返回 `{"kind":"resume"}` 时，结构模型将各数组默认为空。业务校验会报 `PROFILE_INVALID`，但详情只有各区名称。模型返回两条相同 `item_id` 时只带 `duplicate_count` 等信息。Job 重试允许 `reason=empty_profile` 或 `reason=duplicate_item_id`，当前错误生产处没有发出，所以这两种失败都不可重试。Worker 的首次纠正也未接入这两类。[重复 ID 错误](../../../../backend/app/services/text.py#L281) · [空结果错误](../../../../backend/app/services/text.py#L428) · [解析纠正](../../../../backend/app/workers/runner.py#L613) · [显式重试判断](../../../../backend/app/services/jobs.py#L341)

1. 补齐结构和证据错误生产端的稳定原因。至少让空结果与重复 ID 使用 Job 层已定义的两项原因，标记来源为模型输出，并保留必要的安全字段路径及数量。重试和纠正复用同一套经过选择的解析错误类型，减少新增错误漏接恢复规则的情况。
2. 原文存在且包含可解析内容时，模型首轮输出为空或条目 ID 重复，可以发一次有针对性的校正请求。仍失败时同一 Job 允许用户显式重试或手工核对，使用现有次数、版本和输入前置条件。空原文、已确认结果和过期版本继续按各自错误处理。不要把用户确认提交的空结果或重复 ID 当作 AI 重试。
3. 分别测试空对象、四个显式空数组及重复 ID。覆盖一次纠正成功、两次都失败、同 Job 下一次成功和耗尽。加入空原文、历史任务兼容、状态查询无模型调用的断言。

## 5. 历史 Job 的消息与部分详情仍绕过诊断过滤（P2）

**已用合成历史任务复现。** 给旧记录的 `error.message`、`actual=` 和 `reason=` 分别放入合成标记。当前 Job API 直接使用数据库消息，详情中的自由 token 经过字符正则后也会显示。Worker 的 feedback / 动作日志在部分键上使用同类正则，例如任意 ASCII 的 `reason=` 可直接通过。Android 对原始消息仍只替换换行并截断。此测试说明兼容读边界未完整脱敏，未用于检查用户历史记录是否含敏感内容。[Job API 消息投影](../../../../backend/app/services/jobs.py#L392) · [详情和记录过滤](../../../../backend/app/core/diagnostics.py#L350) · [Android 过滤](../../../../android/app/src/main/java/com/mockmate/app/ui/ErrorDiagnostics.kt#L597)

1. 为 Job 错误读出建立安全视图。可识别的固定中文错误消息保留；无法识别的历史消息回退到服务端错误码的标准文案。历史重试判定仍读取兼容信息，展示脱敏无需改历史记录。避免将同一份原始历史消息再送入诊断复制或 Toast。
2. 按值的来源过滤详情，枚举型的 `stage/reason/source/status` 使用固定取值，计数和相似度验证数字，字段路径沿用 schema 约束。自由的 `actual/expected` 只保留能确认的固定枚举或经过专门校验的值。只在值来自当前服务端对象时保留必需的引用 ID。诊断记录、API 和 Android 保持一致，保留用户确认表单中必要的合法字段定位。
3. 添加合成历史消息、理由和实际值标记用例，分别断言 Job API、记录和剪贴板无内容标记。兼容正例验证旧任务仍可重试，“缺组织／职务”和出题槽位等必要诊断仍可读。
