# MockMate AI 解析新任务恢复与校验边界整改指南

当前工作区的上一轮用例已覆盖同材料退出后重开、重开页面回读失败、连续标签的多段工作经历、空结果和重复条目，以及历史错误消息和详情的过滤。本轮复验发现四组边界问题。后端 253 个现有测试、Android 121 个现有单元测试通过，Debug APK 构建、契约和地基校验通过。只读核查确认原真机失败任务仍可重试，并保留了缺失组织和职务的诊断。复现用合成材料和模拟 HTTP，未调用真实模型、重试历史任务或进行真机复验。

按第 1、2 节优先修复用户无法恢复和错误经历入草稿的问题。保留原有 Job ID、重试预算、版本保护、计划 3+3、证据引用与公开响应契约。

## 1. 提取完成后发起新解析，回读结果失败时页面无法恢复（P1）

**已用 Android JVM 专项探针复现。** 在核对页等待文件提取成功后，当前材料的 `latest_job_id` 指向提取任务。用户在同一页点击 AI 解析，服务端返回一个新的解析 Job。现有 `Inform` 分支更新了全局 `job` 和查询状态，却没有同步材料的 `latest_job_id`。若解析成功后回读材料返回 503，错误分支把新解析 Job ID 与旧提取 ID 比较后跳过 `FAILED` 更新，而轮询已在此错误后停止。探针确认仅发出一次解析 POST，但页面继续显示等待且无法只读查询。上一轮测试从「打开页面时服务端已指向解析任务」开始，未走「同页刚收到新的解析回执」的入口。[接收解析回执](../../../../android/app/src/main/java/com/mockmate/app/ui/AppViewModel.kt#L1523) · [处理任务状态](../../../../android/app/src/main/java/com/mockmate/app/ui/AppViewModel.kt#L3460) · [回读错误判断](../../../../android/app/src/main/java/com/mockmate/app/ui/AppViewModel.kt#L3540) · [轮询退出](../../../../android/app/src/main/java/com/mockmate/app/data/JobWatch.kt#L76)

1. 在解析、提取的写入回执进入状态投影前，确认当前账号、页面、材料 ID、revision 和任务类型一致，再把本次权威回执的 Job ID 同步到核对页使用的同一份任务状态。若继续使用 `material.latest_job_id` 和 `materialJobLookup` 两处字段，需在一次状态更新中同步写入。也可由核对页状态统一提供当前任务 ID。必须覆盖首次回执已经是终态的幂等返回。
2. 对当前 Job 的状态查询或结果回读失败时显示可恢复状态，查询按钮读取该解析 Job 的 ID。用户再次点击只查询 Job、材料与快照。保持不同材料、不同版本和旧 attempt 的迟到事件隔离，避免旧提取任务反向替换新解析 Job。已有有效正文和手动填写保持可用。
3. 在现有 Android 恢复测试中模拟「材料已有正文，最新 Job 是已完成提取 → 点击解析 → 回执 queued → 轮询 succeeded → 结果回读 503 → 点击只读查询 → 取得有 profile 的材料」。断言解析 POST 只发生一次，恢复 GET 查询的是 **新解析 Job**，不出现永久加载。补齐立即成功回执、失败回执、过期提取回调三种用例。

## 2. 工作经历的显式字段可被职责文字中的实体替代（P1）

已用解析结构模型和业务校验复现。合成材料是一条完整经历：

```text
公司：示例甲实验室
职位：后端实习生
职责：为数据实习生编写上手手册，并对接示例乙银行。
```

使用整条经历作为引文时，真实的“示例甲实验室／后端实习生”可以通过，也能通过“示例甲实验室／数据实习生”与“示例乙银行／后端实习生”。分段校验已限制引用范围，组织和职务仍是在引文中任意位置搜索。职责里的对象或合作方就能成为错误字段。错误结果可进入待核对草稿，用户确认后会进入后续匹配和出题。[组织和职务当前校验](../../../../backend/app/services/text.py#L562) · [原文分段](../../../../backend/app/services/text.py#L215)

1. 复用已有显式组织与职务字段识别。某个字段在本段明确标注时，从该字段的值范围核对模型值。继续允许全半角、空格和同字段内的连续换行差异，优先保留原文表达。职责、时间、合作方和其它字段的文本不能用于覆盖显式字段。分别判断公司和职位，一项有明确标签就使用它的约束。
2. 标签和字段值解析应复用现有分段与原文位置，避免另写一套互相冲突的分隔规则。兼容无标签且可确定字段的现有正例。遇到标签值冲突或不能可靠定位时走已有 `ungrounded_work_experience` 纠正、重试或人工核对。引文继续逐字来自同一段，手动确认保持原有规则。
3. 测试上述两个独立反例、正确结果、英文 `Company/Title/Responsibilities`、字段值折行、合法无标签版式和连续多段标签。加入一次 Worker 纠正用例，确认错误对象未持久化，校正后保存正确组织和职务。

## 3. `thinking` 参数值被拒绝时仍会误判成参数不支持（P2）

用 HTTP MockTransport 验证，上一轮的数字 `loc` 已得到一次 HTTP 与受控 `AI_REQUEST_REJECTED`。但下面两个合法的错误响应结构仍会触发 **两次 HTTP 并设置 `_thinking_unsupported=True`**：

```json
{"error":{"code":"invalid_parameter","param":"thinking","message":"Unsupported value for thinking.type; expected enabled or disabled"}}
```

```json
{"detail":[{"loc":["body","thinking"],"type":"value_error","msg":"Unsupported thinking mode value"}]}
```

问题来自特定参数或顶层路径分支中对 `unsupported/not allowed` 等泛化词的匹配。参数值错误只应按原响应归类；误设置能力标记还会使同一 Provider 实例后续跳过已配置的参数。[400 错误分类](../../../../backend/app/ai/provider.py#L156) · [回退和能力标记](../../../../backend/app/ai/provider.py#L1121)

1. 明确区分「接口没有该顶层参数」和「该参数的值或模式不被接受」。只有明确的未知参数、顶层字段多余等信号，才允许去掉该参数回退一次。消息回退需把“未知／不支持”的语义绑定到顶层参数本身。对于值、类型、模式、组合配置错误，保持原错误与能力状态。
2. 给上述两个例子添加独立断言，要求 1 次 HTTP、受控错误，并检查后续合法请求继续按配置发送 `thinking`。保留明确不支持、内容过滤、畸形信封和深嵌套的正反例。

## 4. 历史 Job 的错误信封仍有未过滤字段，异常类型能使状态查询失败（P2）

用合成历史 Job 复现两种情况。给 `error.code` 和 `error.request_id` 放入普通文本标记时，Job 投影会原样携带两个标记。把 `error.details` 置为整数 `123` 时，详情过滤尝试迭代整数，抛出 `TypeError`。本次用的是合成记录，未发现真实用户记录存在这些值。之前的消息和合规详情投影继续可用。[Job 错误信封投影](../../../../backend/app/services/jobs.py#L445) · [详情过滤](../../../../backend/app/core/diagnostics.py#L901)

1. 按历史错误对象进入系统的边界规范化类型。只从映射对象读取已定义字段，详情仅接受字符串列表，异常容器回退为空列表或统一占位符。让重试判断和 Job 投影都容忍异常错误体，避免任意一个字段让整个状态查询失效。
2. 错误码从已知集合选取，保留可信的任务错误码及必要兼容项，找不到时回退到通用错误。后台 Job 的请求 ID 保留有效追踪标识；无法验证的历史值可用服务端 Job ID 作关联。对外格式仍为 `ErrorInfo`。旧的错误消息和详情安全过滤继续复用，保护诊断复制和 Toast。
3. 构造历史错误体为非对象、`details` 为整数或含混合元素、错误码与请求 ID 含合成标记的记录，验证状态 GET 一直可用，且标记不会进入 API 和 Android 诊断。再验证原有简历缺字段诊断、同一 Job 可重试、各类正常错误码仍能正确展示。
