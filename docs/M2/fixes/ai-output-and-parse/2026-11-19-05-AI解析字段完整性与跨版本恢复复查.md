# MockMate AI 解析字段完整性与跨版本恢复复查

复查上一轮整改。普通的「提取完成 → 同页解析 → 回读 503 → 只读恢复」已由 Android 新增测试覆盖，后台任务错误体异常、参数值错误触发回退、带职责标签的组织和职位替换也有用例拦住。现有后端 256 项、Android 124 项测试通过，Debug APK、契约与地基检查通过。只读检查确认最初失败的解析任务仍可重试，缺失组织和职位的诊断也保留。以下三个场景仍需补齐。

## 1. 职责无标签或任职值被截短时，错误字段仍可入草稿（P1）

用当前 `ResumeProfile` 和 `validate_profile` 验证下列合成反例，均被接受：

| 原文 | 错误返回 | 当前接受原因 |
| --- | --- | --- |
| `公司：示例甲实验室`、`职位：后端实习生`，下一行未标「职责」，直接写 `为数据实习生编写手册。` | 单位正确，职务为 `数据实习生` | 无标签职责行被当成职位字段的续行，最终使用子串匹配 |
| `公司：示例大学出版社`、`职位：前端工程师助理` | 单位为 `示例大学`，职务为 `前端工程师` | 显式字段值中的任意子串都可通过，组织实体和职务限定词被截掉 |

原案例加上「职责」标签后，错误返回会被拦截。两种反例中的正确组织和职位仍可通过。错误只会先进入待核对草稿，用户确认后会成为后续分析的事实。[显式字段续行处理](../../../../backend/app/services/text.py#L443) · [字段值校验](../../../../backend/app/services/text.py#L505)

1. 有显式标签时，先识别字段本身的值。值已完整后，只有存在明确的排版续行证据时，才把后续文字接入字段。复用当前已支持的 PDF 折行，避免把无标签的叙述句、项目说明和职责当成职位。
2. 组织和职务使用完整值比较，保留已有的大小写、全半角、空格和换行归一化。若原文明确提供别名，可在已有规则允许的范围识别；任意子串不能自动作为别名。无法确定字段边界时，沿用单次纠正和人工核对，避免推断单位或职位。
3. 测试上表两条反例，分别验证错误不可持久化。保留同一段有无职责标签的正确结果、公司后缀和职务限定词，以及前一轮的合法多行 PDF、带日期和无标签正例。另加显式「职位：助理」后跟未标职责的正常短职务，确保没有只靠长度截断。

## 2. 回读材料时切到新版本，核对页没有恢复新任务（P1）

**已用 Android JVM 专项测试复现。** 第一份材料响应为 revision 1，最新解析 Job 已成功。手机为拿到结构回读材料，此时另一设备已编辑并提交 revision 2，新材料响应指向另一解析 Job。当前 `Project` 分支采用了 revision 2 的材料，却保留旧版本结果的 Job 和查询状态。专项测试确认没有发出新 Job GET，页面继续加载，解析与查询入口均隐藏。页面还可能显示旧任务的“解析完成”提示。[材料投影](../../../../android/app/src/main/java/com/mockmate/app/ui/AppViewModel.kt#L3400) · [材料回读](../../../../android/app/src/main/java/com/mockmate/app/data/RestoreJobService.kt#L381) · [核对页查询策略](../../../../android/app/src/main/java/com/mockmate/app/ui/screens/MaterialScreens.kt#L374)

1. 按回读后的权威材料版本决定页面状态。旧 Job 的结果只可标记对应版本完成。采用更高版本时，清除旧 Job 的呈现和完成提示，并对当前材料 ID、revision 与 `latest_job_id` 启动一次新的只读恢复。复用现有 scope、去重与失败提示。
2. 新版本没有任务时直接按材料现状显示可用操作。如果服务器仍携带旧任务 ID，查明它属于旧版本后结束恢复，避免循环查询或阻断新版本操作。新任务查询失败则显示只读重查入口。
3. 使用 MockEngine 控制「旧 Job succeeded → 材料 GET 返回 revision 2 和新 Job ID」，断言新 Job 会被读取，最终显示新 Job 的状态。补新版本无任务、仍带旧指针、新查询返回 503 三种变体。所有恢复分支只发 GET，并保持已经获取的新版本原文和手动填写。

## 3. 历史任务显示的错误与实际重试原因不一致（P2）

用合成旧任务验证，可信列 `job.error_code=AI_TIMEOUT`、当前输入仍有效且未耗尽时，`is_retryable` 返回 `true`。如果旧 JSON 错误对象含未知 `code`，GET 投影却显示 `INTERNAL_ERROR`；如果 JSON 为 `null` 或 `{}`，仍可重试但 `error` 为空。任务状态查询保持可用，诊断与真实重试原因出现分歧。[错误对象规范化](../../../../backend/app/core/diagnostics.py#L832) · [重试与 API 投影](../../../../backend/app/services/jobs.py#L436)

1. 在读取失败或中断任务时，按同一优先级确定受控错误码。优先采用已验证的服务端错误列，列为空或非法时再考虑白名单内的旧 JSON 错误码。已知错误列遇到空或损坏的 JSON 时生成最小的安全诊断，保留现有 `ErrorInfo`。成功、运行中、排队中的记录继续按现有契约。
2. 用真实 Job GET 和重试接口验证上面三种旧 JSON 形式。断言错误码、消息和 `retryable` 使用同一受控原因。保留未知标记过滤、正常历史追踪 ID，以及最初缺组织和职位时的可读提示。
